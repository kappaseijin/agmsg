# handoff 記録の最小差分と受入対照（Issue #253 §3.2）

## 0. 答え

**差分を 2 層に分けます。**

```
層 A   #372 の有無に依存しない。handoff の記録そのもの
層 B   #372 が在るときだけ。claim の owner と受領の owner を結び付ける
```

**層 A だけで「渡した」と「読んだ」は分かれます。**
**#372 がマージされなくても、層 A は単独で意味を持ちます。**

---

## 1. 何を分けたいのか

**Issue #253 の要求はこれです。**

> **業務完了と handoff ack を分ける。**

**上流の `messages.read_at` は 1 つの列で 2 つのことを表しています。**

```
渡した（受信者の stdout へ出た）
読んだ／処理した（業務が終わった）
```

**#372 はこれを分けません。** `agmsg_ack_claim` は `read_at` を立てるだけです。

**fork は `message_receipts` で分けています。** そこだけを切り出します。

---

## 2. 層 A — handoff の記録（#372 に依存しない）

### 2.1 表

```sql
CREATE TABLE IF NOT EXISTS message_receipts (
  message_id   INTEGER PRIMARY KEY,
  owner        TEXT NOT NULL,
  handed_off_at TEXT NOT NULL,
  evidence     TEXT NOT NULL
);
```

**fork の定義をそのまま使います。**

**`evidence` は「どの経路が渡したか」を表す短い語です**（fork の実測値: `inbox_stdout`、
`watch_stdout`、`check_inbox_stdout`、`codex_inline_turn_start`）。

### 2.2 API

```
storage_record_receipts <team> <agent> <evidence> <id>...
    渡した直後に呼ぶ。冪等（INSERT OR IGNORE）
    戻り値 0 = ok / 13 = runtime_error

storage_receipt_status <team> <id>
    receipt        受領が記録されている
    legacy_read    read_at は立っているが受領の記録が無い（この差分より前の行）
    （空）          どちらも無い
```

**`legacy_read` が要るのは、差分を入れる前から在る行と区別するためです。**
**「記録が無い」を「渡していない」と読ませないための三値です。**

### 2.3 呼び出し点

**stdout への書き出しが成功した直後、既読を立てる前。**

**この順序が契約の中身です。** 逆にすると、渡す前に渡したことになります。

### 2.4 上流版では `events` の間接を落とす

**fork の実装は `events.legacy_id` 経由で message_id を解決しています。**
**上流に `events` 表はありません。**

**上流版は `messages.id` を直に使います。** 間接は fork 固有の事情です。

### 2.5 記録の失敗をどう扱うか — **fork の中で割れています**

| 呼び出し側 | 失敗時 |
| --- | --- |
| `scripts/watch.sh` | **診断を出す**（`storage_record_receipts failed after stdout delivery (status N)`） |
| `scripts/inbox.sh` | **握りつぶす**（`2>/dev/null \|\| true`） |

**契約は `watch.sh` の形を採ります。**

```
受領の記録に失敗しても、配送の成否は変えない
ただし黙って捨てない。失敗したことを診断へ残す
```

**握りつぶすと、受領が無いのが「渡していない」のか
「渡したが記録に失敗した」のか区別できません。**
**§2.2 で `legacy_read` を分けた意味が消えます。**

---

## 3. 層 B — claim と受領を結び付ける（#372 が在るときだけ）

```
受領の owner は、その message を claim している owner と同じであること
```

**#372 の `claims.owner` と `message_receipts.owner` を突き合わせます。**

**ack の前提に受領を要求しません。**
**要求すると、受領の記録に失敗しただけで ack が止まります**（§2.5 と矛盾します）。

**代わりに「受領の無い ack」を検出可能にします。** 止めるのではなく、見えるようにします。

---

## 4. 受領は排他ではありません

**`message_id` が PRIMARY KEY なので、1 メッセージにつき受領は 1 行です。**
**`INSERT OR IGNORE` なので、最初に渡した者が残ります。**

**2 つの受信者が同じメッセージを表示した場合、受領は 1 行しか残りません。**

**したがって受領は二重配送を抑止しません。証拠を残すだけです。**
**抑止は §3.1（claim）の仕事です。**

**ここを混ぜると、「受領が 1 行だから 1 回しか配送されていない」と読めてしまいます。**
**読めません。**

---

## 5. 受入対照

### 5.1 層 A

```
正  渡した直後に receipt が 1 行できる。evidence が経路名を表す
正  同じ id を 2 回記録しても 1 行のまま（冪等）
正  この差分より前の行は legacy_read として区別される
負  記録を失敗させると、配送は成功したまま診断が残る（握りつぶさない）
負  受領の記録を消すと、status が receipt から空へ変わる
```

### 5.2 中断（`unknown` から移した 2 件）

```
inbox_interrupted   stdout の後・既読の前で中断したとき、receipt が残るか
watch_interrupted   同上
```

**PR #269 ではこの 2 件は `unknown` でした。**
**受領を入れると、この問いに答えられるようになります。**

**ただし「残る」が正解とは限りません。**
**stdout の途中で落ちた場合、渡したと言えるかは契約の書き方次第です。**
**本書は「stdout への書き出しが成功した直後」と定めた（§2.3）ので、
書き出しが完了していなければ受領は残らないのが正しい挙動です。**

**対照はその通りになることを確かめるものであって、
receipt が在ることを確かめるものではありません。**

### 5.3 層 B（#372 が在るときだけ）

```
正  claim した owner が渡すと、receipt の owner が一致する
負  別の owner が渡すと、不一致として観測できる
```

### 5.4 §3.1 側へ足す対照（依頼で指定されたもの）

```
claim 済みの message は、別 owner の claim 経路には現れない
```

**これは #372 の実装に対する対照です。本書の差分の対照ではありません。**
**§3.3（重複表示の抑止）は、この対照が通ることで得られます。**

---

## 6. #372 がマージされない場合

**層 A はそのまま使えます。** `claims` 表を参照していません。

**層 B だけが宙に浮きます。** その場合、受領の owner は
「渡した席の名前」であって「claim の owner」ではなくなります。
**意味は弱まりますが、証拠としては残ります。**

**#372 は 2026-07-12 から更新がありません。**
**層 A を先に出せる形にしたのは、この可能性のためです。**
