# 型ベース方式は #279 に適用できるか（Issue #279）

## 0. 答え

**適用できない。**

**#274 と #279 は、症状が同じ型でも、欠陥の種類が違う。**

| | #274 | #279 |
| --- | --- | --- |
| 欠陥 | **配線**。観測の結果が判定へ届かない | **被覆**。検査が見ている入力が不完全 |
| 判定は結果を受け取っていたか | **受け取っていない**（捨てられていた） | **受け取っている**（`missing` は必ず判定へ入る） |
| 型で守れるか | **守れる**（届かない書き方を成立させない） | **守れない**（型は見えない名前を見えるようにしない） |

**型ベース方式は「値が判定へ届くこと」を保証する道具である。**
**#279 の問題は、届いた値がそもそも不完全なことであり、届き方ではない。**

**したがって、設計を 2 回作らずに済ませることはできない。**
ただし**別方式を新たに設計する必要もない。** 既存の設計（PR #285 でマージ済み）がそのまま使える。
**直すのは守備範囲の書き方 1 箇所だけである**（§2）。

---

## 1. なぜ適用できないか

### 1.1 #279 の判定経路には、配線の隙間が無い

`tests/windows/lifetime_case.py` の現状:

```python
missing = helper_refs(script) - set(kept) - stubbed - external_helpers(root)
if missing:
    raise UnresolvedReference('unresolved helper references: ' + ', '.join(sorted(missing)))
```

**`missing` は計算されたその場で判定へ入っている。**
受けて捨てる余地も、既定値で迂回する余地も、取り違える相手も無い。

**#274 で塞いだ穴が、ここには最初から存在しない。**

### 1.2 欠陥は `helper_refs` の中にある

`helper_refs` は `_[a-z][a-z0-9_]*` にしか一致しない。
**非アンダースコア名は、そもそも `refs` に入らない。**

```
missing = refs - kept - stubbed - external
          ^^^^
          ここが欠けている
```

**型で包めるのは「計算した結果」であって「計算しなかったもの」ではない。**
`Observation` が `bool` を包めたのは、**その `bool` が既に存在していたからである。**
存在しない要素は包めない。

### 1.3 一般形の 2 条件との関係

依頼が挙げた一般形のうち、前 2 つは**#279 では既に満たされている、または適用対象外**である。

| 一般形 | #279 での状態 |
| --- | --- |
| 検査は「呼ばれたこと」でなく「結果が判断に届いたこと」を見る | **既に届いている**（§1.1）。改善の余地が無い |
| 静的な構文検査の近似ではなく実行時の構造で保証する | **`build_case` は既に実行時に送出する。** 静的検査ではない |
| **守備範囲は目的ベースで書く** | **満たしていない。§2 で直す** |
| 新設の試験自身に変異を当てる | 既存設計 §2.6 の #3 が該当する（§3 で確認） |
| 追加した検査が CI から実行されることを確認する | **実測で確認した**（§3） |

**適用可否の問いへの答えは「適用できない」だが、一般形のうち 2 つは未達である。**
**そこは直す。**

## 2. 直すこと — §2.3.3 を目的ベースへ書き換える

**既存設計 §2.3.3 は、防げる入力と防げない入力を列挙している。**

```
| `_typo_helper` を呼ぶ（未定義）        | 検出する |
| `zqx_no_underscore_fn` を呼ぶ（未定義） | 検出しない |
| 非規約名のヘルパを fixture へ新設する   | 検出する |
```

**これは #274 で撤回したのと同じ形である。**
`2026-09-06T174500_...` §3.5 の初版は迂回手段を列挙して失敗した。
**数え漏れがそのまま嘘になる。**

**目的で切り直す。**

> **fixture の中で定義される名前を対象とする。fixture の外で解決される名前は対象としない。**

`build_case` は fixture のテキストから関数を切り出して組み立てる。
**そこに定義がある名前は、この検査が責任を持つ。**
**外部コマンド・シェル組み込み・他ファイルのヘルパは、この検査の責任範囲ではない。**
それらと未定義の呼び出しを区別するには、シェルの字句解析が要る（既存設計 §2.2 の実測）。

### 2.1 保証していること（実測で確かめる範囲）

| 誤り | 結果 |
| --- | --- |
| fixture へ規約外の名前で関数を定義する | `UnresolvedReference` |
| 規約に従う名前の未定義呼び出し | `UnresolvedReference`（現状も検出する） |

**この表は「落ちることを実測した誤り」であって、「落ちる誤りのすべて」ではない。**

#### 既知の穴（例。網羅ではない）

**規約外の名前の未定義呼び出しは検出しない。** 外部コマンドと区別できないためである（既存設計 §2.2）。
**ただし、そのヘルパを fixture へ定義した時点で `build_case` が落ちる。**

**この例も「漏れのすべて」ではない。**
**何を守るかは目的で書き、何が漏れるかは例で書く。** 例を数え上げて範囲を定義しない。

### 2.2 なぜ「fixture の外」を対象にしないか

**対象にしようとすると、誤検出が残る。** 既存設計 §2.2 の実測では、
名前の種類を広げると誤検出が 33 件から始まり、マスク処理を重ねても 1〜3 件残った。

**誤検出が残る検査は「またあれか」で無視されるようになり、検査として死ぬ。**

**責任範囲を狭く宣言して、その範囲では確実に落ちるほうがよい。**

## 3. 一般形の残り 2 条件（実測）

### 3.1 CI から実行されるか — 確認した

`.github/workflows/tests.yml:1095`:

```yaml
run: python -m unittest discover -s tests/windows -p 'test_lifetime_*.py' -v
```

**`test_lifetime_case.py` はこのパターンに一致する。** 実測:

```
Ran 21 tests in 34.196s
OK
modules: ['test_lifetime_adapter', 'test_lifetime_case', 'test_lifetime_packet',
          'test_lifetime_replay', 'test_lifetime_semantics']
```

**`test_lifetime_case` が discover の対象に入っている。**
#274 で見つかった被覆の欠落（`observe()` が CI の discover を一度も通っていなかった）と
**同じ問題は #279 側には無い。**

> **これは「今そうである」ことの確認にすぎない。**
> **実装で新しいファイルを足す場合は、その名前が `test_lifetime_*.py` に一致することを
> 改めて確かめること。** 一致しなければ、書いた試験は CI で 1 度も走らない。

### 3.2 新設の試験自身への変異

既存設計 §2.6 の #3（**`build_case` から `if bad: raise` を削ると、#2 の試験が FAIL する**）が
これに当たる。**「検査が在ること」ではなく「その結果が生成の可否へ届いていること」を見ている。**

**この対照は維持する。**
