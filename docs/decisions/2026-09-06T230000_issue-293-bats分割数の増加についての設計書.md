# bats 分割数の増加（Issue #293）

## 0. 要旨

**依頼どおり macOS 4→10 / ubuntu 4→6 にしても、macOS は期待した約 7 分になりません。**

投影の結果は **約 10.6 分**（633 秒）で、**偏りは 13% から 68% へ悪化**します。

**律速は分割数ではありません。** 2 つあります。

| 律速 | 内容 |
| --- | --- |
| **重み付け** | 分割の重みが **`@test` の個数**であり、実時間と乖離する。分割数を増やすほど乖離が効く |
| **macOS の同時実行上限** | **アカウントは macOS を同時 5 本までしか走らせない**（`tests.yml` 冒頭の実測記録）。**10 分割は 2 波に分かれ、5 本を超える分は待つ** |

**重みを実測秒へ替えると、同じ 10 分割で 357 秒（6.0 分）・偏り 0% になります。**

**したがって、分割数だけを増やしても割に合いません。**
ランナーを 2.5 倍使って 1.5 倍しか速くなりません。**先に重み付けを直します。**

**本書の実装範囲は段階 1 のみである**（2026-09-06 breaker 訂正）。

| 段階 | 内容 | 本書の扱い |
| --- | --- | --- |
| **1** | **ubuntu 4→6 と、重みを実時間秒へ置き換える** | **本書が設計する。実装対象** |
| 2 | macOS の同時実行上限を実測する | 別途の起点依頼 |
| 3 | 実測に従って macOS の分割数を確定する | 別途の起点依頼 |

**`PINNED_APART` の除去も本書の実装範囲外である**（§3.5）。
`#291` / `#294` の間欠 failure と同じ領域（macOS watcher 周り）を触るため、
**同時に変えるとどちらが原因か切り分けられない。** 別 PR とする。

**受入条件 2 の数値目標（約 7 分）は撤回された。**
新しい条件は**「重み付けを実時間秒へ置き換えたうえで、最長 shard 時間と偏りを測り、
改善したことを示すこと」**である。

## 2. macOS の同時実行上限（設計を決める制約）

`tests.yml` の冒頭に、この repository 自身の実測が記録されている。

> **the account runs at most five macOS jobs at once**
> （measured 2026-08-21: 35 runs that day, 140 macOS jobs, queue waits of 0-50 min）

**これが正しければ、macOS を 10 分割しても同時に走るのは 5 本である。**
残り 5 本は 1 波目の終了を待つ。**壁時間は「最長 shard」ではなく「2 波の合計」になる。**

秒重みで 10 分割した場合の見積り: 357 秒 × 2 波 = **約 714 秒（11.9 分）。**
**5 分割で 1 波に収めたほうが速い**（3,569 / 5 = 714 秒。同じ）。

**つまり macOS は、同時実行上限が 5 である限り、どう分割しても約 714 秒（11.9 分）が下限である。**

### 2.1 これは検証が要る

**この 5 という数は 2026-08-21 の実測であり、本設計では再測していない。**
**現在の全 run が 4 分割なので、5 を超えるかどうかは観測できない。**

**上限が実際に 5 なら、macOS を 6 以上に分割する意味はほとんどない。**
**上限がもっと大きいなら、10 分割 + 秒重みで 6.0 分になる。**

**この 1 点で設計の結論が変わる。** §4 で段階を分ける理由である。

## 3. 変更の設計

### 3.1 OS ごとに分割数を変える

現状は 1 つの env が両 OS を兼ねている。

```yaml
env:
  SHARD_TOTAL: 4
...
      matrix:
        os: [ubuntu-latest, macos-latest]
        shard: [1, 2, 3, 4]
```

**OS ごとに数を変えるには、matrix と総数の両方を OS 依存にする。**

**段階 1 は ubuntu 6 / macOS 4 である。** 多いほうへ揃えて、少ないほうを `exclude` する。

```yaml
      matrix:
        os: [ubuntu-latest, macos-latest]
        shard: [1, 2, 3, 4, 5, 6]
        exclude:
          - os: macos-latest
            shard: 5
          - os: macos-latest
            shard: 6
```

総数は step の env で解決する。**global の `SHARD_TOTAL` は廃止する**（2 つの真実を残さない）。

```yaml
        env:
          SHARD: ${{ matrix.shard }}
          SHARD_TOTAL: ${{ matrix.os == 'macos-latest' && 4 || 6 }}
```

**段階 3 で macOS を増やすときは、`shard:` の並びと `exclude` と
この式の 3 箇所を同時に直す。** 3 箇所に散るのは望ましくないが、
**ずれても静かには壊れない**（下記の guard）。

**`exclude` と総数がずれても静かには壊れない。**
既存の guard がそのまま効く。

```yaml
          if [ "$SHARD" -gt "$SHARD_TOTAL" ]; then
            echo "::error::matrix shard $SHARD exceeds SHARD_TOTAL=$SHARD_TOTAL"
            exit 1
          fi
```

`exclude` を書き忘れれば macOS の shard 5 が `SHARD_TOTAL=4` で起動し、**その場で落ちる。**

### 3.2 ジョブ名から分割数を外す

```yaml
    name: bats (${{ matrix.os }} ${{ matrix.shard }}/4)     # 現状。4 が固定
```

**`/4` が嘘になる。** OS ごとに総数が違うので、名前に総数を書けない。

```yaml
    name: bats (${{ matrix.os }} shard ${{ matrix.shard }})
```

**必須チェックの名前は変わらない。** `tests.yml` が

> Keep the required check name stable even if the shard count changes.

と書いているとおり、必須なのは集約ジョブ `bats` であって shard ではない。
**shard の名前は自由に変えてよい。**

### 3.3 被覆の検証は既にある。触らない

```yaml
      - name: Verify the shards covered the whole suite
        run: |
          expected="$(find tests -maxdepth 1 -name '*.bats' | LC_ALL=C sort)"
          for os in ubuntu-latest macos-latest; do
            actual="$(cat manifests/bats-manifest-"$os"-*/shard-files.txt | LC_ALL=C sort)"
            if [ "$actual" != "$expected" ]; then ...
```

**これは受入条件 4（試験の総数が変わっていないこと）を既に満たしている。**

- **どこにも割り当てられないファイル**があれば `actual` が短くなり不一致
- **2 つの shard に重複して割り当てられた**ファイルがあれば `actual` に重複が出て不一致

**「速くなって緑」という最悪の壊れ方は、この検証が既に止める。**

**分割数を変えても、この job は OS ごとに全 manifest を `cat` するだけなので変更不要である。**

**投影でも確認した**: 4 / 6 / 10 / 12 のいずれでも **118 ファイル**（`tests/*.bats` の総数）が
ちょうど 1 回ずつ現れた。

### 3.4 重みを実測秒へ替える（§1.4 の効果を得るために必要）

**`shard-tests.sh` の重みを `@test` 個数から実測秒へ替える。**

スクリプトのヘッダは、秒の表を持つことを一度検討して**却下している。**

> a checked-in table of measured per-file seconds, buys ~150s more but goes stale silently

**却下の理由は「静かに古びる」ことである。** これは正しい懸念だが、**古びても壊れない。**
同じヘッダがそう書いている。

> the property that matters is coverage, not balance: the worst case of a bad weight is
> an unevenly filled shard, never a missing file.

**古い重みの最悪は「偏る」であって「落ちる」ではない。**
**そして現状の `@test` 個数も、既に偏っている**（10 分割で 68%）。

**設計としては次の形にする。**

1. `.github/data/bats-weights.tsv` に `<ファイル名>\t<秒>` を置く（macOS の実測を使う。遅いほうに合わせる）
2. `shard-tests.sh` は、表に**在る**ファイルはその秒を、**無い**ファイルは
   **表の中央値**を重みにする
3. 表に無いファイルがあっても**落とさない。** 被覆は変わらない
4. **表の鮮度を検査しない。** 古びることを受け入れる（上記の理由）

**新しい試験ファイルが表に無くても、中央値が入るので極端な偏りにはならない。**
**0 を既定にしてはならない。** 0 だと新しいファイルが全部 1 つの shard へ寄る。

### 3.5 `PINNED_APART` は現状に合っていない

`shard-tests.sh` は 2 ファイルを固定 slot へ先置きしている。
**その根拠は 2026-08-19 の測定である。**

```
tests/test_remote_engine_start_refusal.bats    722s /  9 tests = ~80s/test
tests/test_remote_status_liveness.bats         380s / 31 tests = ~12s/test
```

**今日の実測では、この 2 ファイルは 99 秒と 93 秒である。**

```
11.0s/test    99s /   9  tests/test_remote_engine_start_refusal.bats
（test_remote_status_liveness.bats は 93s / 31 tests = 3.0s/test）
```

**722 秒だったファイルが 99 秒になっている。** スクリプトのヘッダ自身が予告していたとおりである。

> FOLLOW-UP: whichever of that effort's PRs (#876 et al.) touches either file named below
> changes its real cost ... drop or replace entries here based on what it says then

**秒重みへ替えるなら `PINNED_APART` は不要になる。**
**重みが実時間そのものになるので、「個数では測れない重さ」という概念が消える。**

**ただし削除は本書の実装範囲外とする**（2026-09-06 breaker 訂正）。
`#291` / `#294` の間欠 failure と同じ領域を触るため、**同時に変えると切り分けられない。**
**別 PR で行う。** 秒重みだけを先に入れても効果はほぼ変わらない（§1.5、差は 2 秒）。
**残すと、軽いファイル 2 つが shard slot を先取りして、かえって偏る**
（実測: 現行スクリプトの 10 分割 633 秒に対し、pin を外した単純 LPT では 515 秒）。

## 4. 段階を分ける

**§2 の同時実行上限が未検証なので、macOS の分割数を先に決められない。**

### 段階 1: ubuntu 4→6 と、重みの置き換え

**この段階には未検証の前提が無い。**

- ubuntu 4→6: **576 秒 → 416 秒**（count 重み）、**336 秒**（秒重み）
- macOS は **4 のまま**、重みだけ替える: **943 秒 → 892 秒**
- 同時実行本数が増えるのは ubuntu だけ。**ubuntu の上限は macOS より緩い**

**壁時間は macOS が決めているので、この段階では全体はほとんど速くならない。**
**それでも先に入れる理由は、重みの置き換えが macOS の効果の前提だからである。**

### 段階 2: macOS の同時実行上限を実測する

**段階 1 を入れた状態で、macOS を 10 分割にした PR を 1 本作り、
10 ジョブの `started_at` を見る。**

```bash
gh api repos/<owner>/<repo>/actions/runs/<id>/jobs \
  --jq '[.jobs[]|select(.name|test("macos"))|{name,started:.started_at,queued:.created_at}]'
```

**5 本が同時に始まり、残り 5 本が遅れて始まるなら、上限は 5 である。**
**10 本が同時に始まるなら、上限は 10 以上である。**

### 段階 3: 実測に従って macOS の分割数を決める

| 段階 2 の結果 | macOS の分割数 | 期待される最長 |
| --- | --- | --- |
| 上限が 5 | **5** | 約 714 秒（11.9 分）。**これ以上は速くならない** |
| 上限が 10 以上 | **10** | **357 秒（6.0 分）** |

**上限が 5 だった場合、macOS をこれ以上速くする手は分割ではない。**
その場合は「最も遅いファイル群を短くする」か「macOS で走らせる範囲を狭める」になるが、
**後者は breaker が既に却下している。** 前者は本件の範囲外である。

## 5. 受入条件への対応

| 受入条件 | 対応 |
| --- | --- |
| 1. macOS 4→10、ubuntu 4→6 | **段階 1 では ubuntu 4→6 のみ実施**（§3.1）。macOS の分割数は段階 3 で確定する |
| 2. **重み置換後の最長時間と偏りを測り、改善を示す**（数値目標は撤回） | **§1.5 で投影済み。** macOS 943→894 秒（偏り 13%→0%）、ubuntu 576→347 秒（偏り 29%→12%）。**CI での実測は実装時に行う** |
| 3. 偏りを実測 | **§1.3 / §1.4。** count 重みでは 68% へ悪化し、秒重みでは 0% になる |
| 4. 試験の総数が変わっていないこと | **既存の job `Verify the shards covered the whole suite`（`tests.yml`）が保証する。** `find tests -maxdepth 1 -name '*.bats' \| sort` と、OS ごとの全 manifest（`bats-manifest-<os>-*/shard-files.txt`）を `cat` して `sort` したものを**文字列として厳密比較**する。欠落なら短くなり、重複なら重複行が出て、**いずれも不一致で落ちる**（§3.3）。投影でも 4/6/10/12 すべてで 118 ファイルを確認 |

**満たすと受入条件 2 が満たせない**（10 分割にしても 7 分にならない）ためです。
**どちらを優先するかは判断が要ります。**

## 7. 確認できていないこと

- **macOS の同時実行上限。** `tests.yml` の 2026-08-21 の記録に依っており、**再測していない**（§2.1）
- **§1.2 の実測は 1 回の run（`34037049929`）に基づく。** 実行ごとの揺れを見ていない
- **ubuntu の同時実行上限。** macOS より緩いと仮定しているが測っていない
- **秒重みの表が古びたときの実際の劣化幅。** 「偏るだけで落ちない」ことは
  スクリプトのヘッダの主張であり、**本設計では確かめていない**
- **`tests/test_ci_sharding.bats` の中身を読んでいない。** `PINNED_APART` の削除が
  この試験に影響するかは未確認（§6 の 6 で実装者へ渡した）
- **照合できなかった秒。** macOS の shard 実測合計 3,697 秒に対し、
  ファイルへ帰属できたのは 3,569 秒（96%）。差はセットアップと帰属に失敗した行である
