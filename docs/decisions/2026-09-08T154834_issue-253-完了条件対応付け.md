# Issue #253 完了条件と既存成果の対応付け

PR #349は公開経路の能力を分類し、PR #350は不足するhandoff記録をLayer Aとして
claimから分離した。PR #353はLayer Aの隔離fixtureと判定器を実装し、固定HEADで

ただし、**Layer AのPASSは、F/O互換、B3非依存、Layer BのPASSを意味しない。**

## Layer A PASSが証明しないもの

PR #353の`layer_a=pass`が証明するのは、固定F sourceの隔離rootで次が観測できることだけである。

- handoff後にreceiptとevidenceが残る
- 同一IDの記録が冪等である
- receipt無し既読を`legacy_read`、未該当を`none`として区別する
- receipt記録失敗でも配送成功を維持し、診断を残す
- inbox/watchの消費前中断と消費後・receipt前中断を区別する

次は証明していない。

- F/Oのaggregate互換性
- 公式O経路でのLayer A提供
- B3非依存
- claim ownerとreceipt ownerの結合
- Layer Bの実装と受入

これらはLayer Aの主張へ含めないという境界であり、Issue #253の未完了理由ではない。

## Layer B全面実装前に既存対照で限定できること

既存§3.1と`tests/test_claims.bats`により、次を新しく作り直す必要はない。

1. 1件の未読messageを1 ownerだけが取得する
2. release後に別ownerが再取得する
3. 別ownerのackを拒否する
4. 期限切れleaseを別ownerが再取得する
5. team、recipient、message IDのscopeを保つ

したがって、将来Layer Bを実装する場合もlease機構全体を自動追加しない。
owner/ID結合対照は、**それが無いと採用する最小契約を確定できない具体的な未決事項が
見つかった場合にだけ**、次から必要なものを選ぶ。

1. receiptが在るとき、`receipt.owner == claim.owner`を公開IDで照合できる
2. 別ownerのhandoffを不一致として観測できる
3. claim済みmessageが別ownerのclaim経路へ現れないことを、同じ公開IDで示せる
4. receipt無しackの成功と、handoff証跡が無い理由のunknownを別フィールドで観測できる
5. opaque history IDとclaim IDを暗黙に混同せず、一意に対応付けられる

Layer B未実装、F/O incompatible、unknownの存在だけを理由に、この5点を自動的な
次工程またはIssue #253のclose条件にはしない。

**receipt無しackの成功は、ackの前提にreceiptを要求しないという契約上の結果である。**
一方、receiptが無い理由を導入前行、中断、記録失敗のどれかに特定できないことは
handoff証跡側のunknownである。ack成功と証跡unknownを同じ失敗へ畳まない。

## 不足している能力

- 公式公開経路のmessage単位claim/release/期限操作
- claim ownerとhandoff receipt ownerの公開IDによる結合
- 並行`inbox`/`watch`での重複表示抑止
- handoff後の業務ackと、receipt記録失敗からの回復状態の区別
- receipt無しack成功とhandoff証跡unknownを別々に返す状態表現

## 残るunknown

- `truncated_history`と`missing_history`でID対応を保てるか
- `legacy_read`が導入前行、中断、記録失敗のどれかを追加証拠なしで区別できるか
- 消費後・receipt前中断でhandoff証跡をどう回復するか
- role lockをmessage単位所有やhost fencingへ広げず、どこまで再利用できるか
- 上流PR #372の`claims`とforkの`message_claims`を統合・移行する方法
- 公式側へLayer Aを提供したときのF/O互換性

これらのunknownは保存するが、解消をIssue #253のclose条件にはしない。
