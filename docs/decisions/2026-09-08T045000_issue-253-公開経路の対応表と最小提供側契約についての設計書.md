# 公開経路の対応表と、不足分だけの最小提供側契約（Issue #253 手番 5）

## 0. 答え

**公式公開経路だけでは足りません。** 最小の提供側契約が要ります（§3）。

**ただし「足りない」の中身を 2 つに分けます。**

```
満たさないことが観測できたもの     -> 契約を求める（3 件）
判定できていないもの（unknown）    -> 契約を求めない。unknown のまま返す（6 件）
```

**依頼文は「満たさぬもの」に「受信中断からの回復」を含めていました。**
**実測ではそれは `unknown` であり、「満たさない」ではありません。**
**そこを分けないと、根拠の無い要求を上流へ出すことになります。**

---

## 1. 対応表（PR #269 / #271 の実測から）

**F = fork 固定版、O = 公式固定版。**

### 1.1 役割の排他 — **公式で満たせる**

| 観点 | F | O |
| --- | --- | --- |
| 役割所有（4 ケース） | pass | **pass** |

**`actas-claim.sh` と active-name `watch.sh` で、1 つの勝者と、
勝者を名指しする 1 つの明示的な held 応答を区別できました**（PR #271、4 ケースとも）。

**ただし付帯条件があります。**

- **表示経路は 4 ケース中 2 ケースが `unknown`。** handoff が `[0,0]` のケースがある
- **観測は有界です。** 初期表示待ち 5 秒＋観測 0.4 秒。**一般の配送保証ではありません**
- **役割ロックは message の ACK・status・回復・host fencing を与えません**（PR #271 の明記）

### 1.2 message 単位の handoff / ack — **公式で満たせない**

| 観点 | F | O |
| --- | --- | --- |
| `claim_owner_release_expiry` | pass | **unsupported** |

**公式側に、公開の claim 操作そのものがありません。**
**owner と期限を持つ排他を、公開入口から取れません。**

### 1.3 重複表示の抑止 — **どちらも満たせない**

| 観点 | F | O |
| --- | --- | --- |
| `inbox_parallel` | **incompatible** | **incompatible** |
| `watch_parallel` | pass | **incompatible** |
| `watch_same_sid_resume` | unknown | **incompatible** |

**`inbox` は F でも O でも、stdout と既読記録の間の障壁で、
同じメッセージを 2 つの受信者へ表示しました。**

**これは「公式に無い機能」ではなく「両方にある欠陥」です。**
**移植では解決しません。**

### 1.4 判定できていないもの — **6 件が `unknown`**

| 観点 | F | O |
| --- | --- | --- |
| `truncated_history` | unknown | unknown |
| `missing_history` | unknown | unknown |
| `inbox_interrupted` | unknown | unknown |
| `inbox_mark_failure` | unknown | unknown |
| `watch_interrupted` | unknown | unknown |
| `watch_mark_failure` | unknown | unknown |

**「受信中断からの回復」はここに入ります。**

**両経路とも、消費失敗の継ぎ目を元へ戻した後に同じメッセージを再表示しました。**
**しかし receipt と cursor の影響を ACK と混同しない、という条件で `unknown` のままです。**

**`unknown` は「満たさない」ではありません。**
**満たすとも満たさないとも言えない、という観測結果です。**

## 2. 依頼文の枠組みを 1 点だけ直す

**依頼文はこう書いています。**

> **満たさぬもの**: message 単位の handoff/ack、**受信中断からの回復**、重複表示の抑止

**「受信中断からの回復」は実測では `unknown` です。**

**`unknown` を「満たさない」へ畳むと、次が起きます。**

```
1  観測していない挙動について、上流へ契約を要求することになる
2  要求した契約が満たされても、元の unknown は解けない
3  解けていないことに気づけない（契約が入ったので済んだと読む）
```

**本書は三値のまま返します。** 二値へ畳みません。

**`unknown` を解くには追加の観測が要ります。**
**それは今回の依頼の範囲外（新規の対照 harness を足さない）なので、
「未判定として残っている」と breaker へ返します。**

## 3. 不足分だけの最小提供側契約

**§1.2 と §1.3 だけを対象にします。** `unknown` は含めません。

### 3.1 公開の claim / release / 期限（§1.2 の不足）

```
要求   対象 team/agent の未読 1 件を、owner と期限つきで排他的に取得できる
       同じ owner が release できる
       期限切れは自動で再取得可能になる
根拠   O は claim_owner_release_expiry が unsupported（PR #269）
```

**F の `claim.sh` が既にこの形を持っています。**
**ただし本書は移植を提案しません。** 契約として何が要るかだけを返します。

### 3.2 handoff の記録を、既読と分ける（§1.2 の不足の続き）

```
要求   「誰へ、いつ、何を証拠に渡したか」を、既読フラグと別に取得できる
根拠   Issue #253 が「業務完了と handoff ack を分ける」ことを求めている
       O には claim 操作自体が無く、handoff の記録も無い
```

**これは §3.1 とは別の要求です。**
**claim があっても、handoff の証拠が無ければ「渡した」と「読んだ」を分けられません。**

### 3.3 重複表示の抑止（§1.3）

**ここは契約を要求する前に、判断が要ります。**

**`inbox` の重複は F でも O でも起きます。両方にある欠陥です。**

```
案A  上流の欠陥として報告し、修正を提案する
     -> fork 側も直る。ただし fork の claim 機構とは別の話になる
案B  claim を前提に抑止する（§3.1 の契約に含める）
     -> claim を入れた側でしか直らない。inbox 単体の欠陥は残る
```

**私は案 A を勧めます。** 欠陥を機能要求へ言い換えると、
**元の欠陥が残ったまま「対応済み」になります。**

**ただしこれは breaker の判断です。** 本書は両案と根拠を示すに留めます。
