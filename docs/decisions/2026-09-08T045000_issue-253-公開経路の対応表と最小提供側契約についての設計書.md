# 公開経路の対応表と、不足分だけの最小提供側契約（Issue #253 手番 5）

## 0. 答え

**公式公開経路だけでは足りません。** 最小の提供側契約が要ります（§3）。

**ただし「足りない」の中身を 2 つに分けます。**

```
満たさないことが観測できたもの     -> 契約を求める（3 件）
判定できていないもの（unknown）    -> 契約を求めない。unknown のまま返す（6 件）
```

**依頼文は「満たさぬもの」に「受信中断からの回復」を含めていました。**
**実測ではそれは `unknown` であり、「満たさない」ではありません。**
**そこを分けないと、根拠の無い要求を上流へ出すことになります。**

## 2. 依頼文の枠組みを 1 点だけ直す

**依頼文はこう書いています。**

> **満たさぬもの**: message 単位の handoff/ack、**受信中断からの回復**、重複表示の抑止

**「受信中断からの回復」は実測では `unknown` です。**

**`unknown` を「満たさない」へ畳むと、次が起きます。**

```
1  観測していない挙動について、上流へ契約を要求することになる
2  要求した契約が満たされても、元の unknown は解けない
3  解けていないことに気づけない（契約が入ったので済んだと読む）
```

**本書は三値のまま返します。** 二値へ畳みません。

**`unknown` を解くには追加の観測が要ります。**
**それは今回の依頼の範囲外（新規の対照 harness を足さない）なので、
「未判定として残っている」と breaker へ返します。**

## 3. 不足分だけの最小提供側契約

**§1.2 と §1.3 だけを対象にします。** `unknown` は含めません。

### 3.1 公開の claim / release / 期限（§1.2 の不足）

```
要求   対象 team/agent の未読 1 件を、owner と期限つきで排他的に取得できる
       同じ owner が release できる
       期限切れは自動で再取得可能になる
根拠   O は claim_owner_release_expiry が unsupported（PR #269）
```

**受入対照**（2026-09-08 breaker 断定で追加）:

```
claim 済みの message は、別 owner の claim 経路には現れない
```

**この対照が、重複表示の抑止を兼ねます**（§3.3）。

**F の `claim.sh` が既にこの形を持っています。**
**ただし本書は独自の起草をしません。** §3.1 は上流 PR #372 をそのまま前提にします（§4）。

### 3.2 handoff の記録を、既読と分ける（§1.2 の不足の続き）

```
要求   「誰へ、いつ、何を証拠に渡したか」を、既読フラグと別に取得できる
根拠   Issue #253 が「業務完了と handoff ack を分ける」ことを求めている
       O には claim 操作自体が無く、handoff の記録も無い
```

**これは §3.1 とは別の要求です。**
**claim があっても、handoff の証拠が無ければ「渡した」と「読んだ」を分けられません。**

### 3.3 重複表示の抑止 — **要求項目から外す**（2026-09-08 breaker 断定）

**本書の初版は案 A（上流の欠陥として報告）と案 B（§3.1 に含める）を並べ、案 A を勧めました。**
**breaker はどちらも採らないと断定しました。**

**案 A を採らない理由**:

```
上流は既に把握している         PR #372 のタイトルが "atomic delivery"
inbox は「表示」であって「消費」ではない
1 席 1 agent の公式モデルでは、複数プロセスが同じ inbox を読む用法自体が想定外の可能性が高い
欠陥と断じる根拠が、fork 側の用法（P2 の broker + worker）にしかない
```

**私は「両方で起きるから欠陥」と読みました。**
**しかし「両方で起きる」は「両方が同じ前提に立っている」でも説明がつきます。**
**公式の前提を確かめずに欠陥と断じていました。**

**案 B を採らない理由**: **重複表示の抑止は claim の帰結であって、要求ではありません。**

**F の `watch_parallel` が pass なのは、F が claim で解いており、
抑止機能を別途足していないためです。**

**扱い**: §3.1 の受入対照へ「claim 済み message は別 owner の claim 経路に現れない」を
足しました。**抑止は対照通過の結果として得られます。**

**本節は「上流 #372 が同じ問題を claim で解いている」という記録として残し、
要求項目からは外します。**

## 4. 上流 PR #372 との突き合わせ

**依頼文は「提供側契約が要ると結論した時点で初めて #372 と突き合わせる」としています。**
**§0 でそう結論したので、ここで突き合わせます。**

> **開示**: 私は依頼を受け取る前、入口判断の「確認できていないこと」を潰す作業として
> **#372 を既に読んでいました。** 依頼文の「この段階では読まなくてよい」より前の行動です。
> **本書の §1 と §2 は #372 を参照せずに書いています。**

| | fork | 上流 PR #372（OPEN） |
| --- | --- | --- |
| claim の表 | `message_claims`（owner, **claimed_at**, expires_at） | `claims`（owner, expires_at） |
| handoff の記録 | `message_receipts`（**handed_off_at, evidence**） | **無い**。ack は `messages.read_at` を立てる |
| PID sentinel | 無い | `receiver-live.sh` |

**#372 は §3.1 を満たします。§3.2 を満たしません。**

**したがって「#372 が入れば足りる」とは言えません。**
**§3.2 の handoff 記録は、#372 とは別に要求する必要があります。**

### 4.1 提案の骨格は「#372 ＋ §3.2」（2026-09-08 breaker 断定）

```
§3.1  上流 PR #372 をそのまま前提にする。独自に起草しない
      fork の message_claims との差分（claimed_at の有無、表名）は
      「#372 に合わせる」向きで扱う
§3.2  #372 に無いので、これだけを fork から切り出し、#372 の上に載る差分として設計する
```

**独自に起草しないのは、重複提案になるためです。**

**#372 は 2026-07-12 から更新がありません。**
**マージされない可能性を織り込みます。**
**その場合でも §3.2 の設計は無駄になりません。**「何を分けるべきか」は #372 の採否と独立です。

**表の名前が違う点も記録します。** `claims` と `message_claims` は別の表であり、
**#372 がマージされると fork に 2 つの claim 表が並びます。**
**移行は本書の対象外ですが、事実として残します。**
