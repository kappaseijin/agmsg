# #253 / #247 / #246 のどれが入口か（Issue #222）

## 0. 答え

**3 件の間に、着手を止める依存はありません。**

**入口は #253 です。** breaker が既に最優先と断定しており、
**依存の見立てもそれを否定しません。**

**ただし #247 と #246 の性格は大きく違います。** そこは以下で分けて示します。

---

## 1. 依存関係の見立て

### 1.1 硬い依存は無い

| | 何を必要とするか | 他の 2 件を待つか |
| --- | --- | --- |
| **#253** | 公開の**通信**経路（send / inbox / api.sh messages） | **待たない** |
| **#247** | 公開の**所有権照会**経路 | **待たない** |
| **#246** | 公開の**登録照会**経路 | **待たない** |

**#247 の本文が「B1 の registration 照会とは独立した設計・実装 PR にする」と明記しています。**
**#253 が必要とするのはメッセージ経路であり、登録・所有権の照会ではありません。**

**したがって「どれが前提か」という問いへの答えは「どれも前提ではない」です。**

### 1.2 硬くない依存はある — 語彙の共有

**3 件とも、同じ区別を必要とします。**

```
#247  不明を所有者なしと扱わない
#246  対象外・欠落・破損・読取失敗・未対応版を区別する
#253  handoff と ack を分け、確認できなかったことを成功にしない
```

**「確認できなかった」を「無かった」に読み替えない、という同じ要求です。**

**先に着手した 1 件が、この区別の言い方（状態名・終了状態・観測の有効期間）を決めます。**
**後続はそれに合わせるほうが、契約が揃います。**

**これは着手を止める依存ではありません。** 順序を決める材料です。

## 2. 台帳の `official` は #247 の入力になるが、#246 の入力にはならない

**依頼の 2 番目の確認事項です。実測しました。**

| ファイル | `official` | `agguild` |
| --- | --- | --- |
| **`scripts/lib/actas-lock.sh`** | **2** | 19 |
| `scripts/api.sh` | **0** | 6 |
| `scripts/identities.sh` | **0** | 6 |
| `scripts/whoami.sh` | **0** | 4 |

| `scripts/lib/api-actas-owner.sh` | **0** | 1 |
| `scripts/lib/api-registrations.sh` | **0** | 1 |

### 2.1 #247 には既に上流へ返せる材料が 2 件あります

**`actas-lock.sh` の `official` 2 件は、次の内容です。**

```
owner を読めない lock を unknown として非 0 で返す契約の説明
owner が読めない場合を unknown として扱う。参照関数は上流
```

**これは #247 の主張そのものです。**

> **consumer が対象 team/agent の観測時点の owner と照会状態を公開入口から取得し、
> 不明を所有者なしと扱わない。**

**「不明を所有者なしと扱わない」という意味論の中核は、fork に既にあり、
台帳の判定では上流へ単独で適用できます。**

**#247 の上流提案は、ゼロからではなく、この 2 件を起点に組み立てられます。**

### 2.2 #246 には上流へ返せる材料が 1 件もありません

**registration 照会に関わる 21 hunk は、すべて `agguild` です。**

**`--all-projects`、`--name`、`roster contract`、`api-registrations.sh` は
いずれも fork 固有の概念で、上流に対応物がありません。**

**#246 の上流提案は、既存の fork 実装の切り出しではなく、新しい契約の起草になります。**

**これは #246 が難しいということであって、後回しにすべきということではありません。**
**ただし「fork の実装を整理すれば上流提案になる」という見込みは立ちません。**

### 2.3 #253 の材料

| ファイル | `official` | `agguild` |
| --- | --- | --- |
| `scripts/drivers/storage/sqlite.sh` | 4 | 6 |
| `scripts/send.sh` | 1 | 4 |
| `scripts/inbox.sh` / `check-inbox.sh` / `history.sh` | 0 | 7 |
| `scripts/claim.sh` / `lib/claims.sh` / `message-status.sh` | 0 | 3 |

**lease / ack の機構そのもの（claim / receipts / message-status）は全て `agguild` です。**

**`sqlite.sh` の `official` 4 件は UTF-8 と stderr の扱いで、lease/ack とは無関係です。**
**`send.sh` の `official` 1 件は UTF-8 の入力検証で、これも無関係です。**

**#253 が「公式の公開経路だけで必要挙動を満たせるか」を判定するとき、
fork 側の機構は判定の材料にはなりますが、上流へ出す材料にはなりません。**
**#253 の本文が「B3 全機構移植や上流 PR 丸ごとの採用は先決しない」と書いているのと整合します。**

## 3. 着手順序の提案

```
1  #253   公開通信経路の lease/ack 依存の判定
2  #247   actas owner 照会契約（official 2 件を起点にできる）
3  #246   registration 照会契約（起点になる official が無い）
```

### 3.1 なぜ #253 が先か

**breaker が最優先と断定しており、依存の見立てがそれを否定しないためです。**

**加えて、#253 だけが「上流を変えずに済むかもしれない」問いを含みます。**

> **必要挙動を公式公開経路だけで満たせれば、P2 契約に B3 非依存の範囲を明記。**

**満たせた場合、#247 / #246 に求める範囲も狭まる可能性があります。**
**逆はありません。** #247 / #246 を先に済ませても、#253 の判定は軽くなりません。

**先に答えが出ると後続の範囲が変わりうるものを先に置きます。**

### 3.2 なぜ #247 が #246 より先か

**#247 には上流へ返せる材料が 2 件あり、#246 には 0 件だからです。**

**材料がある側で「不明・stale・読取不能をどう名づけ、どう返すか」を先に固定すれば、
#246 はその語彙を再利用できます**（§1.2）。

**逆順にすると、#246 でゼロから決めた語彙を、
既に上流適用可能な #247 の 2 件へ後から合わせることになります。**
