# hunk 分類台帳と段階移行計画（Issue #254）

## 0. 要旨

**本書は計画のみである。ファイルの移動・リポジトリの切替・削除・
`agguild` / `agguild_pool` の作成は含まない。**

| 決めたこと | 内容 |
| --- | --- |
| 台帳の単位 | **hunk**（ファイルではない） |
| 台帳の規模 | **267 ファイル / 734 hunk**（§1 の基準で実測） |
| 台帳の鍵 | **hunk の内容から導く 16 桁の id。** 基準を固定するため不変（§2.2） |
| 網羅の保証 | **検査で保証する。** 台帳に無い hunk・台帳にしかない行・分類が空の行を落とす（§3） |
| 負の対照 | **5 種すべて実測済み。** それぞれちょうど 1 件を報告する（§3.3） |
| 実行ゲート | **本計画が受入されても解除しない。** 実行は別途の起点依頼を要する（§6） |

## 1. 基準（受入条件 1）

**次の 2 点を固定する。以降のすべての数はこの基準に対するものである。**

```
fork    7ea795e93683b0e7ede0fabf017fe503fcfe6aea   2026-09-06T02:19:11+09:00
公式    e58dbafad5a84be625f070385bb0c076c3daa4db   2026-09-05T17:21:31+09:00
```

公式は `fujibee/agmsg`（`repos/kappaseijin/agmsg` の `parent`。実測）。

### 1.1 数える手段を固定する（これが無いと数が再現しない）

**基準を固定するだけでは足りない。`git diff` の呼び方で hunk の数が変わる。**

実測（merge-base → fork、同じ 2 点）:

| 呼び方 | hunk |
| --- | --- |
| **`-U0`** | **734** |
| 既定（`-U3`） | **484** |
| `-U10` | 404 |
| `-U0 -w` | **742** |
| `-U0` + `diff.algorithm=minimal` | 735 |
| `-U0` + `patience` | 731 |
| `-U0` + `histogram` | 732 |

**文脈幅を指定しないと 484 になる。** 隣接する変更が 1 つの hunk へ併合されるためである。
**空白を無視すると逆に増える（742）。** 併合されていた hunk が割れる。
**アルゴリズムを変えても ±4 動く。**

**`-U0` だけでは足りない。** 実行環境の `diff.interHunkContext` でも数が変わる。

| `diff.interHunkContext` | hunk（`-U0` 付き） |
| --- | --- |
| **0（既定）** | **734** |
| 1 | 631 |
| 3 | 544 |
| 5 | 507 |
| 10 | **450** |

**`-U0` は hunk の内側の文脈行を決め、`--inter-hunk-context` は hunk 同士をどこまで
併合するかを決める。別の軸である。** コマンドラインで上書きできることを実測した。

```
設定 10 のみ                        450
設定 10 + --inter-hunk-context=0    734
```

**したがって、次のコマンドを台帳の正本とする。**

```bash
GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null \
  git -c diff.algorithm=myers -c core.quotePath=false \
      diff -U0 --inter-hunk-context=0 --no-color --no-ext-diff --no-textconv \
      3d06318 7ea795e93683b0e7ede0fabf017fe503fcfe6aea
```

- **`-U0` と `--inter-hunk-context=0` は両方必須。** 片方では足りない
- **`-w` を付けてはならない**（742 になる）
- **`diff.algorithm` を明示する。** 実行環境の設定に依存させない
- **`core.quotePath=false` を明示する。** 既定は `true` で、非 ASCII のパスを
  `"docs/…\344\270\215…"` の形へクォートする。**この基準には日本語ファイル名が 1 件あり、
  クォートされると `diff --git "a/…" "b/…"` となって `" b/"` を含まなくなる。**
  **§2.2.1 の path 抽出規則がその行で定義されなくなる**（§1.1.1）
- `--no-ext-diff` / `--no-textconv` は外部 diff ドライバの影響を断つ
- `-M` / `--no-renames` はどちらでも 734。**指定しない**

#### 1.1.1 私は自分で足した防御を、自分の測定へ適用していなかった

**層 2（設定源の遮断）を足したとき、digest を測り直さなかった。**

私の global 設定は `core.quotePath=false` だった。
**遮断しない実装で digest を計算していたため、私の環境の設定がそのまま結果に入っていた。**

```
遮断なし（私が測っていた条件）  n=734  path 解析不能=0  digest=258a1e93df7db7fe...
遮断あり（本書が指示した条件）  n=734  path 解析不能=1  digest=1b4c84fc1ef42b98...
```

**「設定を遮断する」と書いた本人が、遮断しないコマンドで数えた値を載せていた。**

**reviewer が記述どおりに実装して 1 件の不一致を見つけたことで判明した**（2026-09-07）。
**reviewer の実装のほうが正しく、私の値が環境に汚染されていた。**

**`-c core.quotePath=false` を明示すると、遮断の有無で値が変わらなくなる**（実測）。

> **このときの値は `ad69a2fd...` だった。**
> **その値は後に誤りと分かった**（§2.2.4。本文の抽出が 1 行多かった）。
> **現在の正しい値は `258a1e93...` である。**
> **`core.quotePath` の是正そのものは正しく、ここでの結論は変わらない。**

> **digest による保証は正しく働いた。** 記述どおりに実装した側が不一致を検出した。
> **仕組みは機能しており、間違っていたのは私の値のほうである。**

#### 列挙では守らない。3 層で守る

**数を動かす設定は、これまでに 2 回、後から見つかっている。**

```
1 回目   -U0 を書いていなかった                    734 -> 484
2 回目   --inter-hunk-context を固定していなかった  734 -> 450
```

**どちらも verifier の独立実測で見つかった。**
**どちらも私の環境では既定値だったため、私の手元では正しい数が出ていた。**
**「自分の環境で正しい」は「どこでも正しい」ではない。**

**列挙を増やす対応では 3 回目が来る。** 3 層に分けて守る。

##### 層 1: 明示指定（既知の軸）

**コマンドラインの明示指定は config より強い。** 実測した。

repository の `.git/config` を意図的に汚染しても、正本コマンドの数は変わらなかった。

| 汚染した local 設定 | hunk |
| --- | --- |
| （汚染なし・1 回目） | **734** |
| （汚染なし・2 回目） | **734** |
| `diff.interHunkContext=3` | **734** |
| ＋ `diff.algorithm=histogram` | **734** |
| ＋ `diff.context=5` | **734** |
| ＋ `diff.wsErrorHighlight=all`（既定で上書きしていないキー） | **734** |
| （後片付け後） | **734** |

**「設定を断った」と「設定が効かなくなった」は別である。**
**この表が示すのは後者である。** 明示指定した軸は、config が何であっても効かない。

##### 層 2: 設定源の遮断（未知の軸のうち global / system 由来）

```bash
GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null \
  git -c diff.algorithm=myers -c core.quotePath=false \
      diff -U0 --inter-hunk-context=0 --no-color --no-ext-diff --no-textconv \
      3d06318 7ea795e93683b0e7ede0fabf017fe503fcfe6aea
```

**これが正本コマンドである。**

**ただし `.git/config`（repository 内の設定）はこれでは断てない。**
**環境変数は global と system にしか効かない。**

##### 層 3: 診断の補助（保証ではない）

**明示指定していない未知の軸が `.git/config` にある場合が残る。**

```bash
GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null \
  git config --list --show-origin | grep -c '\bdiff\.'
```

実測: 汚染時 **4 件**、後片付け後 **0 件**。

**しかしこれは保証ではない。診断の補助である。**

**この式は `diff.*` しか見ていない。**
`core.bigFileThreshold` / `GIT_CONFIG_COUNT` / `.gitattributes` は素通りする
（verifier の指摘、2026-09-07）。

**検出式を広げない。** 広げるのは列挙の延長であり、**5 層目が来る。**

**層 3 の役割は、`header-mismatch` が起きたときに原因の当たりを付けやすくすることである。**
**汚染の検出を層 3 に依存しない。**

> **保証は digest が担う**（次節）。未知の設定が何であれ、
> **件数か digest が変わるので検査は落ちる。**
>
> **「層 3 が守っている」と書かない。** 次に読む人が層 3 の網羅性を信じてしまう。
> **守っていないものを、守っていると書かない。**

##### そのうえで、期待値と突き合わせる

**台帳のヘッダに期待値を持たせ、検査が実際に数え直した値と突き合わせる**
（§2.1.1、§3.1 の `header-mismatch`）。

**ただし、この突き合わせが意味を持つのは「生成」と「検査」が別の実行であるときだけである。**

```
生成時   ヘッダを書く。この時点の突き合わせは無意味（自分と自分を比べている）
検査時   生成器とは別の実行で数え直し、ヘッダと突き合わせる
```

**生成スクリプトが台帳とヘッダを同じ実行で書くなら、
どんな設定で走らせてもヘッダはその結果と一致し、mismatch は起こりえない。**

**したがって次を分ける。**

- **ヘッダは、台帳を作ったときに 1 度書き、commit する**
- **検査は CI で走らせる。** CI の環境は生成した環境と別である
- **CI で数が変われば mismatch になる。** ここで初めて環境差を見ていることになる

**実装時に、この分離が効いていることを変異で確かめること。**

```
CI 側で diff.interHunkContext=3 等を設定する  ->  検査が落ちること
```

**落ちなければ、検査は環境差を見ていない。**

##### 件数だけでは弱い。内容も固定する

**`expected-hunks: 734` は数だけである。**
**設定が変われば、同じ件数のまま中身が入れ替わることがありうる**（境界の切り方が変わる）。

**そこで台帳自身の `hunk_id` 列からダイジェストを作る。**

###### 定義（バイト単位。この記述だけで再計算できること）

```
1  台帳から、先頭が "#" の行と空行を除く
2  各行の第 1 フィールド（TAB 区切りの 1 列目）＝ hunk_id を取り出す
3  LC_ALL=C で昇順に並べる（バイト値の昇順）
4  各要素の後ろに LF (0x0A) を 1 個ずつ置いて連結する
   ＝ 区切りは LF、**末尾にも LF が 1 個付く**
5  そのバイト列の sha256 を小文字 16 進で書く
```

同じことをシェルで書くとこうなる。

```bash
grep -v '^#' <ledger> | cut -f1 | LC_ALL=C sort | shasum -a 256
```

**値（§1 の基準、734 行）:**

```
expected-digest: 258a1e93df7db7fe06334c5d8bb70517e96221b0ea5be9b63bd09b93a42589f1
```

###### なぜ台帳の列から作るのか

**生成過程の中間表現から作ると、循環が残る。**
**生成器が持っている値を生成器が検算しても、何も確かめたことにならない。**

**`hunk_id` 列は台帳に見えている。** 台帳と本書があれば、
**生成器を見ずに誰でも同じ値を計算できる。**

**受入条件**: **verifier が本書の記述だけを読み、生成器を見ずに digest を計算し、
ヘッダの値と一致すること。** これが満たされて初めて digest は循環を破る。

###### 実測（正・負の対照）

| 条件 | digest |
| --- | --- |
| **正: 上の定義で 1 回目** | **258a1e93df7db7fe...** |
| **正: 同じ定義で 2 回目** | **258a1e93df7db7fe...**（一致） |
| 負: **末尾 LF を落とす** | 3dcc84af60ae2883...（**変わる**） |
| 負: 区切り無しで連結（旧定義） | f109d13c52f8b2ab...（変わる） |
| 負: 台帳から 1 行抜く | d4b892d081988e58...（変わる） |
| 参考: `LC_ALL=en_US.UTF-8` で並べる | 258a1e93df7db7fe...（**変わらない**。id は 16 進のみ） |

**末尾 LF の有無で値が変わる。** だから定義に書いた。
**ロケールは本件の id では影響しないが、`LC_ALL=C` を指定に含める**（将来 id の文字種が
変わったときに黙って変わらないように）。

#### 正本コマンドの定義元を 1 つにする

**設計書と実装の 2 箇所にコマンドがあると、片方だけ変わったときに検出できない。**

**台帳生成スクリプトを唯一の定義元とし、設計書と台帳ヘッダはそこから引用する。**
**検査はスクリプトの定義を使って数え直し、ヘッダと突き合わせる。**

**層 2・層 3・定義元の一本化は、いずれも verifier の独立実測と breaker の判断による**
（2026-09-07）。
**初版は `-U0` すら書いておらず、書かれたとおりに数えると 484 になった。**
**「基準を固定した」だけでは再現性は得られない。**

### 1.2 二点間の差分を台帳の対象にしてはならない

**`git diff <公式> <fork>` は 281 ファイル / 881 hunk を返す。**
**しかしこれを台帳の対象にすると誤る。**

この差分には**公式が分岐後に進めた分**が混ざっており、
それは「fork 側が加えた独自拡張」ではない。**符号が逆に現れるだけである。**

**分岐点（merge-base）を測ってから、両側を別々に数える。**

```
merge-base  3d06318  2026-08-22T12:47:31-07:00
```

| | 対象 | ファイル | hunk |
| --- | --- | --- | --- |
| **A** | **fork 側の変更**（merge-base → fork） | **267** | **734** |
| B | 公式側の変更（merge-base → 公式） | 37 | 171 |
| C | **両側が触ったファイル**（衝突候補） | **23** | — |

**台帳の対象は A である。**

**B（公式側 171 hunk）は台帳の対象外である。衝突候補の判定にのみ用いる。**
**「未分類」ではない。** 対象外であることと、未着手であることを区別する。
**B を分類しようとしないこと。**

C は移植時に衝突を起こしうる。**実測では 23 件のうち 7 件が実際に衝突した**（§1.6）。

### 1.3 #248 の 257 件とは直接比較できない（受入条件 2 の前半）

**正本コマンド（§1.1）で測ると fork 側は 267 ファイル / 734 hunk である。**

**Issue #248 の「257 件」は、測定コマンドが不明であり、直接比較できない。**

§1.1 のとおり、**同じ 2 点でも呼び方で数が変わる**（734 / 484 / 404 / 742）。
**#248 がどの呼び方で測ったかは記録されていない。**
既定（`-U3`）で測っていたなら、そもそも比べているものが違う。

**したがって「10 件増えた」とは言えない。** 初版はそう書いていたが**撤回する。**

**#248 の一覧は旧 cutoff の原差分であり、移植確定の台帳ではない。**
本書はその一覧を引き継がず、**§1.1 の正本コマンドで数え直している。**

> **これは「数が違う」ではなく「比べられない」である。**
> 測定条件を書かない数は、後から別の条件で測った数と並べられない。

#### 計画への影響

**順序の制約がかかるのは 7 件であって 23 件ではない。**

`conflict_risk` 列は 2 値ではなく 3 値にする。

```
conflicts     実測で衝突した（7 件）。移植の順序に制約がかかる
touched       両側が触ったが自動 merge できた（16 件）。注意はするが制約ではない
no            片側しか触っていない
```

**この実測を、台帳の行生成より先に行った**（breaker 指示。2026-09-06）。
**734 行を分類してから「実は衝突していた」と分かるより安い。**

## 2. 台帳

### 2.1 スキーマ

**1 行 1 hunk の TSV とする。** 列は次のとおり。

| 列 | 内容 |
| --- | --- |
| `hunk_id` | §2.2 の 16 桁 id |
| `path` | ファイルパス |
| `owner` | **`official` / `agguild` / `pool` / `exception` のいずれか。空・その他は「未分類」** |
| `disposition` | `adopt`（公式へ提案）/ `port`（agguild へ移す）/ `drop`（廃棄） |
| `rationale` | その判断の理由。**空は不可** |
| `public_dep` | 公開 API・契約への依存（無ければ `none`） |
| `regression` | 対応する回帰試験。**無ければ `none` ではなく `needed`** |
| `conflict_risk` | `conflicts` / `touched` / `no`（§1.6） |
| `assignee` | 担当席 |
| `status` | `unclassified` / `classified` / `verified` |

**TSV を選ぶ理由**: 734 行を人が読み、`git diff` で変更を追い、
`awk` / `sort` で機械が検査するのに、列区切りが確定している形が要る。
**YAML は 734 件のとき差分が読みにくく、JSON は人が直接編集しにくい。**

置き場所: `docs/migration/222-hunk-ledger.tsv`。

### 2.1.1 台帳ファイル自身に測定条件を書く

**設計書に書くだけでは足りない。**

**台帳は 734 行のデータファイルとして単独で残る。**
**それを受け取った誰かが既定の `git diff` で数え直すと 484 になり、
「250 行足りない」と読む。**

**データの意味は、データと一緒に移動しなければ失われる。**

**先頭に `#` で始まるヘッダを置く。**

```
# agmsg fork hunk ledger (Issue #254 / #222)
# base-merge:  3d06318...
# base-fork:   7ea795e93683b0e7ede0fabf017fe503fcfe6aea
# base-upstream: e58dbafad5a84be625f070385bb0c076c3daa4db
# command: GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null
#          git -c diff.algorithm=myers -c core.quotePath=false
#          diff -U0 --inter-hunk-context=0 --no-color --no-ext-diff --no-textconv <base-merge> <base-fork>
# git-version: 2.54.0
# precondition: `git config --list --show-origin | grep -c '\bdiff\.'` must be 0
# expected-hunks: 734
# expected-files: 267
# expected-digest: 258a1e93df7db7fe06334c5d8bb70517e96221b0ea5be9b63bd09b93a42589f1
#                  grep -v '^#' <ledger> | cut -f1 | LC_ALL=C sort | shasum -a 256
#                  (LF-separated AND LF-terminated; see the design doc for the byte-level spec)
# NOTE: the count depends on this exact command AND on git config. -U3:484, -U10:404,
#       -w:742, diff.interHunkContext=10:450, core.quotePath=true changes one non-ASCII path.
#       Trust expected-hunks/expected-digest, not your own diff.
#
# columns: hunk_id  path  owner  disposition  rationale  public_dep  regression  conflict_risk  assignee  status
```

#### 2.1.2 ヘッダの値は人が書かない

**7 回の指摘は 7 種類ではなく、1 つの型が 7 回出たものである**（breaker 認定、2026-09-07）。

> **仕様（書いたもの）と、値（自分の環境で出したもの）が別々に作られており、
> 仕様どおりに実行するまで食い違いが見えない。**

**`core.quotePath` の件が最も純度が高い。**
私は「設定を遮断する」と仕様に書き、**遮断しない環境で出した値**をヘッダへ書いた。
**両者が食い違っていることは、記述どおりに実装した人が現れるまで分からなかった。**

**行を直しても、次の値でまた同じことが起きる。手順を変える。**

```
今まで   仕様を書く／別に自分の環境でコマンドを実行して値を得る／ヘッダへ書く
         -> 2 つが食い違っても、誰かが仕様どおり実行するまで分からない

これから 正本コマンドを実行するスクリプトが、ヘッダそのものを出力する。
         人はその出力をそのまま入れる。手で計算しない。手で書き写さない
```

**「転記の誤りを検査する」のではなく「転記を無くす」。**

生成スクリプトは `--emit-header` でヘッダ行だけを出力する。
**台帳を作るときは、その出力をそのままファイルの先頭へ置く。**

##### これは §1.1 の「循環」の指摘と矛盾しない

**循環が問題になるのは「同じ実行が、書いた値を自分で検算する」場合である。**

**ここで無くしているのは転記であって、独立性ではない。**
**独立性は、CI が別の実行で数え直すこと（§7.5 の条件 2）が担っている。**

```
生成時   スクリプトがヘッダを出力する。人は転記しない  <- 転記の誤りが無くなる
検査時   CI が別の実行で数え直し、ヘッダと突き合わせる  <- 独立性はここ
```

**検査はこのヘッダも突き合わせる**（§3.1 に `header-mismatch` を追加）。
**ヘッダの `base-*` が検査の使う基準と違えば落とす。**
**ヘッダだけ直して中身を直さない、という経路を残さない。**

### 2.2 hunk の鍵をどう作るか

**行番号を鍵にしてはならない。** 前の hunk が変わると全部ずれる。

**基準が固定されているので、hunk の集合は不変である。** したがって**内容から鍵を導ける。**

#### 2.2.1 定義（バイト単位。この記述だけで再現できること）

**入力は §1.1 の正本コマンドの標準出力を LF で分割した行の並びである。**

```
1  「diff --git 」で始まる行に当たったら、その行から path を取り直す
     path = その行の 最初の " b/" より後ろ全部
            （"b/" 接頭辞は含めない。"a/" 側は使わない）

     **その行に " b/" が無ければ、そこで停止する**（fail-closed）。
     path を空文字列にしたり、直前の path を引き継いだりしない。
     正本コマンドは core.quotePath=false を明示しており、クォートは起きない前提である。
     **前提が崩れたなら止める。静かに別の値を出さない。**

2  「@@」で始まる行に当たったら、そこから新しい hunk が始まる
     range = その行を "@@" で分割した 2 番目の要素
            （＝ 1 つ目と 2 つ目の "@@" に挟まれた部分。
              前後の空白 1 個ずつを含む。例: " -615 +615 "）
            **2 つ目の "@@" より後ろの関数名ヒントは含めない**

3  それ以降の行のうち、**空でなく、かつ先頭 1 文字が "+" / "-" / 半角空白 の行だけ**を
   本文へ加える
   **空文字列の行は加えない。**（出力を LF で分割すると末尾に空文字列が 1 個できる。
   これを本文へ入れると、最後の hunk だけ 1 行多くなる。§2.2.4 参照）
   **先頭が "\" の行（"\ No newline at end of file"）は加えない**
   （次の "@@" 行または "diff --git " 行に当たったら、その hunk は終わり）

4  body = 3 で集めた行を LF で連結したもの。**末尾に LF は付けない**

4.5  **検算する**: `range` が宣言する行数（`-m,a +n,b` の a + b。
     数を省略した側は 1）と、body の行数が**一致しなければ停止する**（fail-closed）。
     **この検算は、3 の取りこぼし・拾いすぎをその場で捕まえる**（§2.2.4）

5  payload = path + NUL(0x00) + range + NUL(0x00) + body
     文字コードは UTF-8。復号できないバイトは置換文字へ倒す（errors="replace"）

6  hunk_id = sha256(payload) の小文字 16 進の **先頭 16 文字**
```

#### 2.2.2 なぜここまで書くか

**「hunk_header の範囲部分」とだけ書いた初版は、複数の読み方ができた。**

reviewer が 4 通りに解釈して計算し、**どれも digest と一致しなかった**（2026-09-07）。

```
解釈 1  範囲＝数値レンジのみ、body を rstrip     -> f53cf5b6...
解釈 2  範囲＝@@ 行全体（関数ヒントを含む）      -> ed8c511c...
解釈 3  path に "b/" を含める                    -> 4bd90258...
解釈 4  body を改行付きのまま連結                -> e25f6aa0...
```

**`git diff -U0` の `@@` 行のうち 548 / 734（75%）に関数名ヒントが付く**（実測）。
**「範囲部分」がこれを含むかどうかで値が変わる。**

**digest の計算方法（並び・区切り・末尾・ハッシュ）が明確でも、
その入力である `hunk_id` が一意でなければ再現できない。**

**曖昧さは、いちばん外側だけでなく、いちばん内側にも入る。**

#### 2.2.3 この基準では検査できない規定が 2 つある

**§2.2.1 の 6 手順のうち、次の 2 つは、この基準の差分では一度も使われない。**

| 規定 | この差分での出現 |
| --- | --- |
| 「先頭が `\` の行を本文へ加えない」 | **0 件**（`\ No newline at end of file` が無い） |
| rename の扱い（`diff --git ` 行から path を取り直す） | **0 件**（`rename` / `similarity` 行が無い） |

**書いてあるが、この基準では正しさを確かめられない。**
**別の基準へ移したときに初めて表面化する。**

**verifier の実測による指摘である**（2026-09-07）。
**「曖昧さが残っていても、このデータでは表面化しない」**。

##### 引き金を検査にする

**「基準を動かすときは確かめること」では、確かめ忘れても気づけない。**
**引き金そのものを検査に入れる。**

検査は、正本コマンドの出力に次のいずれかが現れたら `unexercised-rule` を報告する。

```
先頭が "\" の行            （\ No newline at end of file）
"rename " / "similarity " で始まる行
```

**このとき台帳は通さない**（他の判定と同じく非 0 で終了する）。

**意味は「壊れている」ではなく「§2.2.1 の未検査の規定が、いま初めて使われた」である。**
**digest の再確認を経てから通す。**

実測（本基準）: `\` 行 **0 件** / `rename` **0 件** / `similarity` **0 件**。
**したがって現在この判定は発火しない。**

**「確認済み」とは書かない。** 確認していないものを、確認したことにしない。

##### 未定義の挙動は、実際に 2 つの値を生んだ

**初版は「`" b/"` が見つからない場合」を書いていなかった。**

`core.quotePath` が既定（`true`）の条件で、私と verifier が別々に実装したところ、
**同じ n=734・同じ「解析不能 1 件」でありながら、digest が食い違った。**

```
architect  1b4c84fc1ef42b98...   （直前の path を引き継いだ）
verifier   1e45558ebb1afbbe...   （path を空文字列にした）
```

**どちらも「もっともらしい」実装であり、どちらも仕様には書かれていなかった。**

**書かれていない挙動は、実装ごとに違う値になる。**
**そして両方とも「動いて」しまうので、突き合わせるまで気づけない。**

**`-c core.quotePath=false` を入れればこの経路には入らないが、
それでも規則としては停止条件を書く。** 前提が崩れたことを、静かに通さないためである。

#### 2.2.4 空文字列を 1 行拾っていた（実際に起きた）

**初版の規則 3 は「完全な空行」も本文へ加えると書いていた。これが誤りだった。**

`-U0` の差分に文脈行は無く、**追加された空行は `+` と表現される。**
**本当に空の行は hunk の中身ではない。**
そして出力を LF で分割すると、**末尾に空文字列が 1 個できる。**

**その結果、出力の最後にあった hunk（`uninstall.sh` の `-215,0 +331,23`）だけが
23 行ではなく 24 行になっていた。**

```
規則 3（初版）  uninstall body=24  宣言と不一致の hunk=1  digest=258a1e93df7db7fe...
規則 3（修正）  uninstall body=23  宣言と不一致の hunk=0  digest=258a1e93df7db7fe...
```

**修正後は、734 hunk すべてで「宣言した行数」と「body の行数」が一致する。**

##### verifier の一致は、仕様の正しさを保証しなかった

**verifier は §2.2.1 を独立に実装し、`ad69a2fd...` に一致した。**
**しかしそれは、私の仕様に書かれた誤りを忠実に再現したからである。**

**独立実装が一致することは、仕様どおりであることしか示さない。**
**仕様が意図どおりかは示さない。**

**見つけたのは reviewer である。** id 一覧を突き合わせ、**734 件中 1 件の差**まで絞り込み、
**その 1 件の body 行数が hunk の宣言と合わないことを指摘した。**

**「宣言した行数と body の行数が合うか」は、実装どうしを比べなくても単独で確かめられる。**
**そこで規則 4.5 として検算を仕様へ入れた。**

#### 2.2.5 実測

**上の 6 手順だけを読んで書き直した実装で、同じ値になることを確認した。**

```
hunks: 734  unique: 734
digest: 258a1e93df7db7fe06334c5d8bb70517e96221b0ea5be9b63bd09b93a42589f1
一致: True
```

**16 文字（64 bit）で衝突は 0 件。** 734 件では十分である。

**基準を動かしたら id も変わる。** これは欠点ではなく、
**基準を変えたのに台帳を引き継ぐ、という誤りを検出する仕掛けである**（§3 の `stale` / `missing`）。

## 3. 網羅の検査（受入条件 2 の本体）

**「一覧がある」ことと「その一覧が網羅である」ことは別である。**
**台帳を人が読んで確かめることはしない。検査で落とす。**

### 3.1 検査するもの

固定基準から hunk を数え直し、台帳と突き合わせる。

| 判定 | 意味 |
| --- | --- |
| `missing` | **hunk が台帳に無い**（＝未分類のまま残っている） |
| `stale` | 台帳にあるが hunk が無い（基準が動いた・誤記） |
| `path-mismatch` | id は合うが path が違う |
| `duplicate` | 同じ hunk が二重に載っている |
| `unclassified` | `owner` が空、または既定の 4 値以外 |
| `no-disposition` | `disposition` が空 |
| `malformed` | 列が足りない |
| `header-mismatch` | **ヘッダの `base-*` / `command` / `expected-hunks` / `expected-digest` が、検査が数え直した値と違う**（§2.1.1）。**検査は生成とは別の実行でなければ意味がない** |
| `unexercised-rule` | **§2.2.1 のうち、この基準では一度も使われていなかった規定が使われた**（`\ No newline` 行 / rename）。§2.2.3 |

**この一覧が判定のすべてである。**

**層 3（`diff.*` 設定の検出。§1.1）はここに含まれない。**
**層 3 は判定ではなく診断の補助であり、`header-mismatch` が起きたときに
原因の当たりを付けるために出力する。**
**層 3 の結果だけで通す／落とすことはしない。**

> **層 3 を判定として一覧へ載せない理由**: 載せると、次に読む人が
> **「層 3 が汚染を検出している」と読む。** 実際には `diff.*` しか見ておらず、
> `core.bigFileThreshold` などは素通りする（§1.1）。
> **守っていないものを、守っていると読める場所へ置かない。**

**1 件でもあれば非 0 で終了する。** 部分的に通すことはしない。

### 3.2 実行の場所

**CI で走らせる。** 台帳は 734 行あり、手で確認する運用にすると必ず抜ける。

**`tests/` 配下の試験として置く**（`test_ci_sharding.bats` が分割の被覆を守っているのと同じ位置づけ）。
**名前は既存の discover / shard の対象に入るものにすること。**
**入らなければ書いた検査は 1 度も走らない**（Issue #293 段階 2 で同型の欠落を確認済み）。

### 3.3 負の対照（実測。受入条件 2）

**試作を作り、5 種の変異を当てた。**

| # | 種別 | 変異 | 結果 |
| --- | --- | --- | --- |
| 正 | — | 734 行すべて分類済み | **PASS** |
| 負 A | **受入条件が指定したもの** | **1 hunk を台帳から抜く** | **FAIL `missing: 1`**。抜いた hunk を名指しした |
| 負 B | — | 存在しない hunk を足す | FAIL `stale: 1` |
| 負 C | — | `owner` を空にする | FAIL `unclassified: 1` |
| 負 D | — | `path` を取り違える | FAIL `path-mismatch: 1` |
| 負 E | — | 同じ hunk を二重に載せる | FAIL `duplicate: 1` |

**負 A の出力（実測）:**

```
FAIL {'missing': 1}
   missing: 9b262a83717fc01d .github/enforced-assertions-baseline
```

**どの負の対照も、報告した件数はちょうど 1 である。**
**「何かあると全部赤くする」検査ではない**ことを、この 1 件という数が示している。

### 3.4 検査そのものが壊れた記録

**この検査を書いている最中に、検査自身が偽の結果を返した。**

最初の版は、hunk 列挙のモジュールを `import` した際に**その top-level が走り、
引数で渡した台帳ファイルを hunk 一覧で上書きしていた。**

結果として**正の対照まで `FAIL {'malformed': 734}` を返した。**

```
正   完全な台帳   : FAIL {'malformed': 734, 'missing': 734}   <- 誤り
```

**正の対照を取っていたから気づけた。** 負の対照だけを見ていたら、
**「よく落ちる検査」として通していた。**

`if __name__ == '__main__':` で囲って解消した。**実装時も正の対照を必ず取ること。**

## 4. 「未知」を空欄のまま ready としない（受入条件 3）

**`status` は 3 値で、既定は `unclassified` である。**

```
unclassified   まだ判断していない。既定値
classified     owner と disposition と rationale が埋まっている
verified       independent 実測で裏が取れている
```

**`verified` でない行が 1 件でもある間は、その範囲の実行ゲートを開けない**（§6）。

**空欄を「問題なし」と読み替える経路を作らない。**
検査は `owner` が空なら `unclassified` として落とす（§3.1）。
**「空欄 ＝ 公式責務」のような既定は置かない。**

## 5. 段階移行の計画

### 5.1 登録パスと persona パスを分ける（最重要）

**agmsg の登録は物理パスを鍵にしている。**
`join.sh --project <path>` と `whoami.sh <path>` が同じパスで一致することが前提である。

**したがって persona ディレクトリを `agguild_pool` へ移すと、登録が切れる。**

**この失敗は本セッションで実際に起きている**（2026-09-06、agmsg チーム）。

- architect 席の登録が**作業クローンではなく人格ディレクトリ**に紐づいていた
- `whoami.sh` が `multiple=true` を返し、席を一意に解決できなかった
- **`gh-write-owner-guard` が fail-closed で PR 作成を拒否した**
- 専用の作業クローンを作り、そのパスで join し直して解消した

**計画は次を分けて扱う。**

| 概念 | 置き場所 | 移行の扱い |
| --- | --- | --- |
| **persona データ**（AGENT.md、kaizen、記録） | `agguild_pool` | 移す |
| **作業クローン**（git remote を持つ実体） | 従来どおり | **移さない** |
| **agmsg の登録 project パス** | 作業クローンのパス | **移さない** |

**「persona を移す」と「登録を移す」を同じ手番で行わない。**

### 5.2 順序

```
1  隔離 fixture      使い捨ての team と DB。稼働中の席を一切含まない
2  限定対象          席 1 つ。停止できるもの（worker など）を選ぶ
3  段階移行          席を 1 つずつ。各段で停止点を通過する
```

**一括で移さない。** 全席一括移動は手順に含めない（§5.5）。

### 5.3 各段の停止点

**次を取得できない状態を、実行の停止条件とする。**
**「取れなかったので先へ進む」を認めない。**

| 取得するもの | 取れないときの扱い |
| --- | --- |
| **未処理メッセージの id 一覧** | **停止。** 移行で失われたか判別できない |
| **ack の境界**（どこまで配送が確定しているか） | **停止** |
| **resume 対象のセッション id** | 停止。resume できないと文脈が失われる |
| **actas の owner**（誰がその役を保持しているか） | **停止。** 二重保持を招く |
| **稼働中の writer の一覧** | **停止。** 同じ DB へ新旧が同時に書く事故を防ぐ |

**取得手段は `inbox.sh` / `message-status.sh` / `actas-claim.sh` の
既存の出力とし、DB を直接読まない。**

> **`message-status.sh` の `notFound` を未達の証拠にしないこと**
> （`agent-team.rule.md` に既知の観測として記録がある）。
> **「取れた」と「取れなかった」を区別する。**

### 5.4 rollback の条件

**各段で、次のいずれかが起きたら直前の状態へ戻す。**

- 停止点のいずれかが取得できない
- 移行後に `whoami.sh` が単一の identity を返さない
- 移行後に `inbox.sh` が移行前と異なる未処理集合を返す
- guard が fail-closed で拒否した

**戻す先は「移行前のパスと登録」であり、DB の巻き戻しではない**（§5.5）。

### 5.5 手順に含めてはならないもの（Issue #254 の 4）

| 禁止 | 理由 |
| --- | --- |
| **新側で処理した後に、古い DB snapshot を復元する** | 処理済みの結果が消える。**巻き戻しではなく破壊である** |
| **同じ live DB へ旧新の writer を同時接続する** | 書き込みが競合する |
| **全席の一括移動** | 失敗したときに切り分けられない |
| **GC（不要データの一括削除）** | 移行の成否と独立に判断すべきである |

**これらは「やらないほうがよい」ではなく「手順に書かない」。**
**書けば、いつか実行される。**

## 7. worker へ委譲する範囲

**Issue #254 が「収集手順が決まった反復だけ worker へ委譲する」と定めている。**

| 作業 | 担当 |
| --- | --- |
| 台帳の**行の生成**（734 行の id と path を機械的に出す） | **worker** |
| **`tests/` の 323 hunk の分類**（多くは対応する `scripts/` の分類に従う） | **worker**（下記の条件つき） |
| `scripts/` の 264 hunk の分類 | **architect**（設計判断を伴う） |
| `docs/` の 92 hunk の分類 | worker |
| **実測で衝突した 7 ファイルの扱い** | **architect**（公式追従の判断を伴う） |
| 検査スクリプトの実装 | programmer |
| 台帳の網羅の独立実測 | **verifier** |

**分類は起草にあたるため breaker へは振らない**（`agent-role.rule.md`。breaker は決定・起草・実装・検証をしない）。
**1 席で持てない量なら architect を増員する**（`architect2` 等。`agent-team.rule.md` の連番規約）。

**worker へ渡すときは手順を渡す。目的だけを渡さない。**
**判断が要る形で渡すと、そこで止まるか、勝手に判断される。**

`tests/` を worker へ渡せる条件: **「対応する実装 hunk の owner をそのまま継ぐ」
という規則で決まるものに限る。** 対応先が決まっていない試験は `unclassified` のまま残し、
architect へ戻す。

## 7.5 この設計を「確定」と呼べる条件

**「パラメータをすべて見つけた」ことを条件にしない。** 列挙は原理的に終わらない。

**「見つけていないパラメータがあっても壊れない」ことを条件とする。**

```
1  verifier が、本書の記述だけから digest を再計算し、ヘッダの値と一致すること
   （生成器を見ずに。§1.1 の定義がバイト単位で書けているかの検査でもある）

2  生成器とは別の実行（CI）で検査が走り、
   わざと設定を汚した状態で落ちることが実測されていること
```

**この 2 つが満たされれば、未知のパラメータが何個あっても構わない。**
**digest を動かすので検査に捕まる。**

> **旧い基準（「新しいパラメータが出なければ確定」）は撤回した**（breaker 判断、2026-09-07）。
> **パラメータの列挙は終わらないので、終わらないものを終了条件にしない。**
