# 現PMを変更しないP2 pilot導入・受入

## 結論・決定の出所

agmsgチームに検証専用の`agmsg_pm_pilot_claude`を1席設け、専用clone・専用起動profile・専用記録先で純正Claude Code TUIを検証する。
現在の`agmsg_pm_claude`は停止・再開・claim変更・設定変更を一切しない。
pilotはユーザー窓口を引き継がず、Issue #230/#236を所有・更新しない。
P2成功はP3への自動昇格ではない。

本書は設計だけであり、席の登録・起動、実装、試験Issue作成、本番変更は行わない。
起草はarchitect、接続実装とpilot操作は別依頼後のprogrammer、formal reviewはreviewerが固定HEADの全差分を一括走査する。
P3現PM交代・P4横展開・Issue #239・README変更は対象外である。

方式の正本はPR #240の純正TUI＋正常時deny＋独立監査、およびPR #242/#243の文字列claim統合である。
依頼に引用された「pilotと現PMの移行手順」表は、確認したPR #237の文書にはなく、却下済み`2026-09-05T171009_issue-236-production-rollout.md`に存在した。
今回ユーザーが明示した専用席・P2受入条件だけを本書で改めて定義する。
旧host/UI置換、print-mode運用、旧文書のP3手順は復活させない。

これは一つのP2運用契約だが、接続実装の独立した主張は起草前にPRを分ける。
旧fixtureを本番adapterとして改名するだけの接続は受け入れない。

## 起動adapterの契約

pilot実装は固定checkout内のhelperを使い、既存インストール済みagmsgの正式通信・claim経路へ接続する。
code rootとruntime rootを区別する。
binding/identity/auditのclaim参照先は実際の正式runtime root、rosterは実agmsg登録、送受信とwatchも同じ正本を使う。
模擬roster、別run配下の影claim、team DB複製で本番接続を装わない。

現guardのMonitor許可は`__dirname/watch.sh`を正本とするため、専用checkout helperと正式watchのrootを分ける場合は接続変更が必要である。
launcherで固定した正式watchのcanonical絶対path・digestを検証する契約へ拡張し、任意環境変数のpathを許可しない。
変更範囲はpilot helper側に限る。既存watchや現PMのguard配置は変更しない。
このroot整合を隔離試験で満たせなければ起動ゲートを閉じる。

launcherは正式rosterの一意なteam/agent/type/projectを確認し、session ID、PID、pidStart、新generationを確定する。
正式claim手順でpilot名だけを`${sessionId}.${pid}`としてclaimし、LF付き文字列ownerを照合する。
他ownerがある場合は停止し、無条件release、bare SIDへの縮退、強制奪取はしない。
bindingを世代固有pathへ原子的に公開し、その後同PIDを保つexecで純正CLIを起動する。
SessionStart・actas・watchが同じprocess tokenを使うことを実測する。
初回hookの時点でbinding/claim未成立なら通常作業を拒否する。会話/質問以外を汎用bootstrap例外にしない。

freshは新session ID、resumeは明示した同一session IDと新generation/PID/pidStartを使う。
`--continue`で「最新」を選ばず、保存したpilot SIDに限る。
CLIの引数・有効profile・versionは起動manifestへ残す。認証値は記録しない。
純正interactive起動を使用し、`--print`、独自host、全permission bypassをP2運用へ持ち込まない。
既存リマインダーやMonitorとの実効組合せを確認し、未確認の設定源を黙って無効化しない。

## 最小brokerと検証用Issue

operatorは別の検証用Issueを`kappaseijin/agmsg`へ作成する。
タイトルは`[P2 pilot] Issue #236 受信・委譲・記録受入`、本文に検証専用・親#236・run-id・対象固定HEAD・終了条件を記す。
作成後の番号をmanifestの`testIssueNumber`へ固定する。未確定のまま起動しない。
pilotがコメントできるIssueはその1件だけであり、#230/#236の本文・状態・labels・assignee変更は禁止する。

P2で接続する操作は`agmsg_receive`、`agmsg_send`、`agmsg_delegate`、`issue_view`、`issue_comment`に限定する。
actor/teamはbindingから固定し、宛先はoperator・worker・reviewerの事前登録した3席のみとする。
受信はpilot宛だけを扱い、他席のinboxを既読化しない。
payloadはoperation別schema・文字数上限・未知field拒否を持ち、helperはshell evalではなく固定argvで正式script/ghへ渡す。
rule読取・記録や7分類の保守操作を再定義しない。P2で未接続の操作は明示拒否し、現PM相当の全機能受入を主張しない。
Monitorは正式watchをpilotのcomposite SID/project/type/nameで起動する限定契約を維持する。

brokerの成功は下流APIの結果を伴う。
sendのqueuedと配送到達と処理開始を分離し、requestId・message ID・返信IDを対応付ける。
Issue書込は本文再取得で実改行と対象一致を確認し、そのURLを返す。
GitHub書込accountはpilot producerのClaude seatに対応する`kappaseijin4claude`を明示し、曖昧なら停止する。
identity/profile/実行されるJS本体とwrapperを含むコード集合のdigestを固定する。wrapperだけ同一でJS差替えを見逃す状態にしない。
失敗後に自動再送せず、結果不明時はrequestIdに対応する下流artifactをoperatorが確認してから再投入する。

## 実施手順

1. managerが実装・操作・formal reviewerを指定する。operatorは採用設計と接続実装のmerge/HEAD/review/checkをGitHubで確認する。
2. operatorは正式team一覧でpilot名の非衝突を確認し、専用clone/profile/検証Issue/run manifestを準備する。既存名があれば勝手に別名や同名再登録へ進まない。
3. 現PMのpane/process識別、claim owner、設定と対象ファイルdigestを正式診断経路でbaselineへ残す。内容や認証値は複製しない。
4. 正式joinでpilotを既存agmsgへ登録する。独立監査・watchdog・外側通知を準備してから、専用タブでnative launcherを起動する。
5. fresh起動の一意binding/claim、native質問・選択UI・会話履歴、限定Monitorの発火と配送を確認する。無害な直接marker操作を依頼し、denyとmarker=0を確認する。
6. operatorが検証Issue番号と一意requestIdをpilotへ送る。pilotは受領し、workerへ「固定のfixture文書の行数を数え、値と対象digestを返信」の定型作業を委譲する。worker結果を受け、pilotが検証Issueへ結果・出所・未検証区分を記録する。
7. 同じrunの未完了依頼1件を保存し、pilotだけを正常終了する。終了・claim解放を確認後、同SIDでresumeする。新generationと旧binding不使用、履歴と未完了依頼の継続を確認し、もう1周の受信→委譲→結果→記録を通す。
8. 下記故障試験を1件ずつ実施し、各件の復旧と健全判定を確認してから次へ進む。故障はpilot専用のcode/profile/log領域だけに注入する。
9. operatorは現PMbaselineとの差分を確認し、指定以外の変更がないことと証拠packetを報告する。reviewerが固定HEADと全観点を一括受入する。
10. 結果を`accepted`または`failed`として検証Issueとmanifestへ同時記録する。現PMへの切替は行わない。終了時はpilotのみを所有者確認付きで停止し、証跡を保存する。

workerへの依頼はコード変更・実API測定ではなく既知fixtureの定型集計であり、pilot自身の調査実行で代用しない。
試験のためのIssue、通信、fixture以外の業務依頼をpilotへ投入しない。

## 故障・対照・受入条件

| ID | 注入・操作 | 合格条件 |
| --- | --- | --- |
| N1 | fresh/resume各1回の正常業務周回 | 各周回で受信ID→委譲ID→worker返信→Issue comment URLが揃う。broker markerだけでは不合格 |
| N2 | native会話・質問・限定Monitor | 実TUIで使用可能、監視対象はpilotのみ。別agentのMonitor commandは拒否 |
| D1 | 直接markerと同じ無害処理をworkerへ委譲 | pilot marker=0、worker marker=1。各回固有のmarkerを使い、事前不存在を確認 |
| D2 | shell連結・rtk wrapper・別tool・宛先/Issue逸脱 | guardまたはadapterが拒否し、対象への副作用0。検証Issueへの正対照は成功 |
| I1 | 同SID並行resume・stale binding | 他ownerを奪わず拒否。正常resumeでは旧世代を再利用しない |
| F1 | pilot brokerを実行不能またはbackend明示失敗にする | 送信/記録が成功扱いされず汎用Bashへ迂回しない。無害な実書込0。復旧後は新requestIdで1回成功 |
| F2 | pilot側hook欠落/timeoutを各1回 | 無害stubの実行可否を記録し、通ったものをdeny成功としない。独立実行metadataとの不一致または設定異常を外側へ通知 |
| F3 | PostToolUse記録だけを停止 | 別collectorが実tool metadataを取得し、判断recordと照合できる。両方同じ生成源なら不合格 |
| F4 | 監査loop停止 | 別watchdogがheartbeat年齢180秒以上を検出。監査loop自身のstdoutに依存しない |
| F5 | 通知配送失敗・復旧 | 未達を正常扱いせず停止状態を保持。復旧後にoperatorとユーザー経路への到達を確認 |
| U1 | 全工程前後の現PM比較 | 現PMのprocess/claim/profileに操作由来の変更0。共有teamへのpilot追加は区別して記録 |

監査周期は60秒、watchdog判定周期は60秒、heartbeat閾値は180秒とする。
閾値超過の最初の成功したwatchdog走査で検知する。OS停止や通知遅延を含む180秒以内到達保証とはしない。
通知先はoperatorのagmsg受信箱と、同じworkspace内の独立監視paneでのユーザー可視警報を必須にする。
このpaneはpilotのtool/claim/brokerを使わず、現在のPMのMonitorも再利用・変更しない。
導入前にユーザーが当該paneの警報を確認できることを確認する。到達の証拠がなければP2未受入とする。
生のCLIログ全体を複製せず、collectorは対象SID/generation/tool ID/tool名/input digest/成否の必要metadataだけを抽出する。
CLIログの未知形式・読取不能・途中書込・collector停止は監査不能として警報にする。
実入力を再構成できない場合に架空のdigestを生成せず、照合不能として停止する。

## 証跡・停止・復旧

manifestはrun-id、testIssueNumber、code HEAD、CLI版、profile/helper集合digest、team/seat/project、世代別SID/PID/pidStart、operator、reviewer、状態を持つ。
状態は`prepared → running → stopped_for_fault → running → awaiting_review → accepted/failed`とし、起動条件未達は`blocked`とする。
復旧は外側operatorが対象pilotを特定して行い、判別不能ならkillしない。
設定修復後は新generationでnative resumeし、identity・deny正負対照・監査・通知を再確認してからrunningへ戻す。
broker失敗を理由に制限解除、global設定変更、現PMの再起動を行わない。

報告には各試験のvalue/cutoff/source/command、期待値、実値、tool/message/artifact ID、未確認事項を残す。
timestampはJST RFC3339、GitHub artifactの投稿時刻はserver metadataを正本とする。
秘密・全文会話・認証設定は保存せず、サニタイズ箇所と理由を明示する。
一件でも未達・不明ならP2を合格扱いしない。時間経過、過去P1のPASS、レビュー通知だけで昇格しない。
formal reviewはGitHubの対象HEADとの一致まで確認し、検証用Issueとstate manifestへ結果を反映する。
親#236へのP2進捗反映は現managerが行い、pilotには権限を渡さない。
本書保存時点では実装・pilot登録・起動・試験・formal reviewはいずれも未実施である。
