# Issue #236 G4 着手前設計論点の解決

> **作成経緯**: codex CLI（architect役割）の週次利用枠がユーザー指示によりリセット確認まで
> 利用停止中のため、本文書はChatGPT Web（GPT-5.6、非Claudeベンダー）が独立に作成した。
> PM（Claude、agmsg_pm_claude）は依頼文の作成、資料添付、受領内容の検証・適用のみを行った
> （Issue #383/PR #384と同じ運用）。

## 1. 目的

本書は Issue #236 P2 の G4 着手前に残っている設計上の曖昧さを解消し、native launcher、最小 broker adapter、独立 collector の実装境界と依存関係を固定する。

G1、G2、G3 は既に受入済みであり、再設計しない。

G4 の前提 provider commit は次で固定する。

```text
0b2117c5f91f7950cc196e52edb188748adfa50a
```

G4 は次の3成果物を別PRとして実装する。

1. pilot専用 native launcher と generation binding
2. G3限定の broker adapter
3. PostToolUseと独立した collector / audit observation

3成果物をmergeしただけではpilotを起動しない。実native CLIでの統合受入、fault injection、およびpilot開始判断は後続ゲートとする。

---

## 2. 設計原則

G4では以下をMUSTとする。

* G1〜G3で固定されたprovider commit、capability集合、consumer operation集合を拡張しない。
* 現行PMが使用するguard、broker、profile、Monitor、bindingをpilotの実験のために変更しない。
* pilotは専用launcherからのみ起動可能な構成とする。
* pilotの実作業経路はG3の5 operation以外へ拡張しない。
* G2の6 capabilityを暗黙に7 capability以上へ増やさない。
* observationとauthorizationを分離する。
* `unknown`、読取不能、複数一致を許可または成功へ縮退しない。
* hook由来の記録だけを独立collectorの観測源にしない。
* component単体試験の合格をpilot統合受入の代替にしない。

## 3. 論点1: guard配線の衝突

### 判断

**既存 `scripts/pm-pretool-guard` は拡張利用しない。pilot専用のguard profileとpilot専用broker pathを新設する。**

既存guardと共通化してよいのは、identity検証等の内部的な純粋helperに限定する。

### 採用構成

概念上、次のように分離する。

```text
current PM
  └─ current PM profile
       └─ pm-pretool-guard
            └─ pm-broker.sh
                 └─ pm-broker.js
                    （既存の広いoperation集合）

pilot
  └─ pilot-only profile
       └─ pilot専用PreToolUse guard
            └─ pilot専用broker adapter
                 └─ G3の5 operationだけ
```

ファイル名そのものは実装時に確定してよいが、例えば以下のような配置が自然である。

```text
scripts/pm-pilot-pretool-guard
scripts/p2-consumer-broker.sh
scripts/p2-consumer-broker.*
```

### 根拠

現行 `pm-pretool-guard` はbrokerの実体を単なる設定値として扱っていない。

`pm-broker.sh` の、

* canonical realpath
* executable属性
* symlinkでないこと
* digest
* binding内 `brokerDigest`

まで照合している。

つまり `AGMSG_PM_BROKER_PATH` だけpilot adapterへ差し替えても通らない。これは意図された固定境界である。

さらに現行guardの `BROKER_OPERATIONS` は、G3の5 operationとは異なり、例えば、

```text
git_maintenance
proxy_git_write
team_provision
bot_collaborator
issue_view
pr_view
seat_start
seat_stop
...
```

など多数のoperationを許可対象としている。

G3は明示的に、

```text
receive
delegate
collect-result
issue-record
observe-owner
```

だけをconsumer operationとしている。

したがって既存guardへpilot branchを追加すると、

1. 現PMのproduction-like経路とpilot経路が同じpolicy codeになる
2. 既存PMの約20 operationがpilot側へ誤って開く危険が生じる
3. pilot変更によって現PMを壊す可能性が生じる
4. G3のleast privilege境界がコード上不明瞭になる

という問題が生じる。

### 規範

pilot guardは **G3の5 operationに対応する固定adapter command以外のBashをMUST NOT allow** する。

現行 `pm-pretool-guard` のoperation集合をpilot profileが継承してはならない。

一方、

* session binding検証
* process generation検証
* PID/pidStart検証
* roster/claim検証
* digest検証

のような機構は意味が同一であれば共通helperへ抽出してよい。

ただし「共有するために現行PMの挙動を変更する」ことはG4では行わない。

## 4. 論点2: observe-ownerとG2 capabilityの不整合

### 判断

**`observe-owner` をG2の第7 capabilityにはしない。**

G4において、B2の既存 `actas-owner` APIを読むための **独立したread-only observation contract** を定義し、broker adapterがその固定契約を使用する。

概念的には、

```text
observe-owner
        |
        v
G4 B2 observation binding
        |
        v
canonical api.sh
  get teams <team> actas-owner <agent>
```

とする。

### 直接呼出しか別契約か

結論は、

**「canonical `api.sh ... actas-owner ...` を呼ぶが、G4側に別契約を置いて固定する」**

である。

単なる自由形式の直接呼出しにはしない。

G4 contractが最低限固定すべきものは、

* canonical executable path
* executable digestまたは固定HEADとの対応
* argv shape
* team
* agent=`agmsg_pm_pilot_claude`
* JSON response schema
* exit status
* `unknown`時の扱い

である。

### 根拠

G3は `observe-owner` を明示的に、

> B2のopaque owner/stateを返す

operationとして扱っている。

同時にG3はG2 capabilityを6個に固定し、capability追加・削除・`not-used`変更時にはG3再設計を要求している。

したがって `actas-owner-v1` のような第7 capabilityをG2 manifestへ追加すると、G4接続ではなくG2/G3の契約変更になる。

これは今回の除外範囲に反する。

一方、brokerが任意の `api.sh` commandを実行できる設計も広すぎる。

したがって、

```text
G2 B3 façade
    = messaging/handoff用6 capability

B2 observation
    = observe-owner専用 read-only dependency
```

として契約面を分離する。

### 規範

`observe-owner` は **authorization capabilityではない**。

返却値が、

```text
unknown
read failure
schema mismatch
multiple/ambiguous
```

の場合、brokerはこれを、

```text
free
absent
allowed
```

へ変換してはならない。

またpilot以外のagentをこのoperation経由で一般照会できるようにしてはならない。

## 5. 論点3: native launcherの配置場所

### 判断

**`spawn.sh --pilot` は採用せず、新規pilot専用native launcherを作る。**

例えば、

```text
scripts/pilot-launcher.sh
```

のような専用entry pointとする。

### 根拠

既存 `spawn.sh` の主責務は、

* teamへのpre-join
* tmux/terminal確保
* type registryからCLI選択
* boot prompt生成
* actas prompt
* resume/fresh選択
* readiness待機

である。

一方G4 launcherには、

* pilot seatの一意roster照合
* pilot agent/type/project固定
* session ID確定
* generation採番
* PID / pidStart binding
* claim整合
* profile digest
* guard digest
* broker adapter digest
* collector対象情報
* generation-specific bindingのatomic publish
* native Claude CLIへの最終exec
* resume時の旧generation拒否

という別の安全境界が必要になる。

これは `spawn.sh` のoptional featureではない。

`--pilot` を入れると、通常agent起動器の中にIssue #236固有のsecurity/policy境界を持ち込むことになり、通常spawnの回帰面も増える。

さらにG4の設計上、

> pilot launcherから起動されたprocessだけがpilotとして成立する

必要がある。

専用entry pointにした方が、この性質をコード構造でも明確にできる。

### spawn.shとの関係

launcher内部から既存のpure helperを再利用することは禁止しない。

例えば、

* type registry
* project resolution
* boot-commandの一部
* session関連の共通utility

がpilot要件を壊さず利用できるなら再利用可能である。

ただし、

```text
pilot-launcher.sh -> spawn.sh --pilot
```

をG4のsecurity boundaryにはしない。

### binding schema所有者

**binding schemaのownerはnative launcher PRとする。**

broker adapterとcollectorはそのschemaのconsumerになる。

bindingには少なくとも、

```text
schemaVersion
team
agent
type
project
sessionId
generation
pid
pidStart
profileDigest
guardDigest
brokerDigest
providerCommit
```

およびcollectorが同一session/generationを識別するために必要な値を含める。

collector実装固有の可変状態をbindingへ詰め込んではならない。

## 6. 論点4: 独立collectorのログ取得元

### 判断

独立collectorの一次観測源は、

**Claude Codeが保存するsession transcript JSONL**

とする。

`pm-posttool-record.js` が生成する `executions.jsonl` をcollectorの一次情報源にしてはならない。

またPreToolUse/PostToolUse hookがcollectorへイベントをpushする方式も一次観測にはしない。

### Claude Code側の取得元

Claude Codeの公式仕様ではsession transcriptは、

```text
~/.claude/projects/<project>/<session-id>.jsonl
```

にJSONLとして保存され、各行はmessage、tool use、metadata等のJSON objectである。

`CLAUDE_CONFIG_DIR` が設定されている場合はそのrootを使用する。

したがってpilot launcherはsession IDとconfig rootを固定し、collectorは、

```text
sessionId
generation
project
CLI version
```

を起動manifestから受け取って対象transcriptを識別する。

**collectorはPostToolUse hookから `transcript_path` を教えてもらうことを必須条件にしてはならない。**

hookが停止しても観測可能でなければF3の意味がなくなる。

### transcript探索

project directory名のエンコード方法をcollector自身で推測することも避ける。

collectorは固定したClaude config root配下から、

```text
<session-id>.jsonl
```

に一致する候補を探索し、

* 0件
* 2件以上
* canonical root外
* 読取不能

を `audit unavailable` とする。

唯一候補を発見した後はcanonical pathをrun manifestへ固定し、そのgeneration中に別pathへ勝手に追随しない。

resumeでは新generationとして再検証する。

### collectorが保存する内容

生transcript全体は複製しない。

必要最小限として、

```text
sessionId
generation
toolUseId
toolName
toolInputDigest
observed completion/success/failure state
source offset または source record locator
observedAt
collector schema/version
CLI version
```

程度に縮退する。

tool入力本文、prompt本文、tool output本文、credentialはcollector artifactへ複製しない。

### executions.jsonlとの照合

構成は、

```text
PreToolUse decision
        |
        +------ decisions.jsonl

PostToolUse
        |
        +------ executions.jsonl

Claude native transcript JSONL
        |
        +------ independent collector
                   |
                   +--- collected metadata

audit
  decisions
      vs
  executions
      vs
  independently collected metadata
```

とする。

これにより、

```text
PostToolUse停止
   ↓
executions.jsonl 欠落
   ↓
transcript側にはtool実行あり
   ↓
不一致検出
```

が可能になる。

### debug logの位置付け

Claude Codeの `--debug-file` はpilot launcherからgeneration固有pathへ固定して有効化してよい。

ただしこれはcollectorの主たる「実tool execution ledger」にはしない。

debug logは、

* hookが発火したか
* matcherが一致したか
* hook exit status
* timeout等

を見る**診断用の第二観測源**とする。

したがって、

```text
transcript = tool execution observation
debug log = hook/runtime diagnostics
```

と責務を分ける。

Claude Code公式仕様では `--debug-file <path>` により既知pathへdebug logを出力でき、hook実行状況もdebug logへ記録される。

### schema変更への対応

transcript JSONL内部の全schemaをagmsg独自の恒久APIとして扱ってはならない。

collectorは必要フィールドだけを認識し、

* 未知record
* 欠損
* 読取途中
* 不完全JSON
* tool-use/result対応不能
* 対応CLI version未検証

の場合に、黙ってrecordを捨てて「正常」としてはならない。

必要なtool metadataを決定できない場合は、

```text
collector_status = unknown / audit_unavailable
```

として警報対象にする。

これがfail-open防止になる。

## 7. 論点5: 3つのG4 PRの依存関係

### 判断

依存関係は次のDAGとする。

```text
             G4-A
   native launcher / binding schema
              |
        +-----+-----+
        |           |
        v           v
      G4-B         G4-C
 broker adapter   collector
        \           /
         \         /
          v       v
       integration gate
```

つまり、

**launcher PRを最初に固定し、その後broker adapterとcollectorを兄弟PRとして実装可能にする。**

broker adapterとcollectorの間には直接依存を作らない。

### G4-A: native launcher

所有するもの:

* pilot起動entry point
* pilot profile binding
* generation model
* binding schema
* session/PID/pidStart binding
* guard/broker/provider digest binding
* run manifestに渡すlauncher metadata
* fresh/resumeのgeneration規則

G4-B/G4-Cはこのfixed HEAD上のbinding contractを使用する。

### G4-B: broker adapter

依存:

```text
G1 provider pin
G2 provider capability
G3 consumer contract
G4-A binding schema
```

collectorへは依存しない。

### G4-C: independent collector

依存:

```text
G4-A binding/session/generation schema
Claude Code fixed/tested CLI behavior
```

G2 providerやbroker内部実装に依存してはならない。

broker adapterのlogをcollectorの情報源にしてはならない。

### merge順序

推奨merge順は、

```text
G4-A launcher
   ↓
G4-B broker
   ↓
G4-C collector
```

としてよい。

ただしこれはGit運用上の線形化であって、設計依存は、

```text
A -> B
A -> C
```

であり、

```text
B -> C
```

ではない。

この差を明記する。

## 8. 論点6: 「最小」broker adapterのスコープ

### 判断

G4 broker adapterは、

**G3の5 consumer operationだけを公開する新規adapter**

とする。

既存 `pm-broker.js` の約20 operationのsubset modeとしては実装しない。

公開operationは厳密に、

```text
receive
delegate
collect-result
issue-record
observe-owner
```

の5個である。

### backend対応

概念上は以下の対応になる。

| consumer operation | backend                                     |
| ------------------ | ------------------------------------------- |
| receive            | G2 `message-peek-v1` + `message-claim-v1` 等 |
| delegate           | G2 `message-send-v1` + handoff関連            |
| collect-result     | G2 peek/claim/release/ack/receiptの必要部分      |
| issue-record       | G3で固定済みtest Issue限定write/read-back経路        |
| observe-owner      | §4で定義したB2 read-only observation contract    |

重要なのは、G2 capabilityをそのままPMに1:1公開するのではなく、**consumer operationが上位API**であることである。

例えばpilotが自由に、

```text
message-send
message-release
message-ack
```

を直接選べる設計にはしない。

adapterがG3 operationの状態遷移を実装するために必要なcapabilityだけ内部使用する。

### 既存pm-broker.jsとの関係

既存brokerはG4 pilotのbackendではない。

```text
pm-broker.js
```

の既存operation集合をpilotへ公開しない。

共通化が可能なのは、

* payload decode
* canonical path検証
* digest helper
* JSON schema helper
* atomic append等

のようにpermission surfaceを持たない内部utilityに限る。

既存brokerからoperation dispatcherをimportして「pilotでは5個だけ見せる」という構成は原則採らない。

理由は、誤設定・guard regression時に既存20 operationへ到達可能になるからである。

### unknown / retry

adapterはG3 contractどおり、

* backendが成功したか不明
* message-send結果不明
* Issue write結果不明
* result ID対応不明

の場合に自動再送しない。

特にwrite系で、

```text
unknown -> retry -> duplicate
```

を起こす設計は禁止する。

## 9. 論点7: fault-testの割当て

### 判断

**各G4 PRは自分が所有するfailure modeのcomponent-level fault testを合格しなければmergeしない。**

ただしF1〜F5の正式なpilot fault-injection受入は、3 PR統合後の別ゲートで再度行う。

したがって、

```text
component test
    ≠
pilot fault acceptance
```

である。

G4 mergeだけでP2 pilot fault test合格とは記録しない。

### 割当て

| fault                 | component PRで要求する試験                                                                      | 最終統合試験                                                         |
| --------------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| F1 broker不能/backend失敗 | **G4-B必須**。backend exec不能、非0、invalid/unknown responseでsuccessを返さず、汎用Bash fallbackを持たないこと | 必須。native pilotから実際に失敗させ、書込0、復旧後new requestIdで一度だけ成功           |
| F2 hook欠落/timeout     | **G4-A部分必須**。profile/binding/guard digest欠落や不整合をlauncher側で拒否。guard内部エラーをdenyへ変換する隔離試験    | **完全試験は統合ゲート必須**。実Claude CLIでhook欠落/timeout時に操作が通り得る現実と外部検出を確認 |
| F3 PostToolUse停止      | **G4-C必須**。`executions.jsonl`が欠落してもnative transcriptからtool metadataを取得し不一致を検出            | 必須。実native CLI sessionでPostToolUseを止めて再確認                      |
| F4 audit loop停止       | **G4-C必須**。heartbeat stale等を別監督経路が異常扱いするcomponent test                                   | 必須。実runで180秒等の設定cutoffを含め到達確認                                  |
| F5 通知配送失敗             | G4-Cでnotification failureをhealthyへ変換しない状態機械の試験を行う                                        | **実配送・復旧確認は統合ゲート必須**                                           |

### F2についての注意

Claude CodeのhookはPreToolUseでtool callを拒否できるが、hookそのものが起動しない状況まで同じhookで保証することはできない。

したがってG4-A単体で、

> hookが欠落しても必ず実行前denyできる

という偽の受入条件を置いてはならない。

F2の本質は、

```text
正常時
  -> synchronous deny

hook infrastructure failure
  -> prevention保証なし
  -> independent observation / alert
```

という既存設計上の残存リスクが実測でもそのまま見えることにある。

### 統合fault gate

3 PR merge後、pilot開始前に別の固定HEAD統合gateを置く。

そのgateで、

```text
N1
I1
F1
F2
F3
F4
F5
```

を一連のnative CLI runとして検証する。

この統合gateを通過するまで、

```text
pilot_ready = false
```

とする。

## 11. G4着手順序

G4 implementation handoffは以下の順とする。

### G4-A — native launcher / pilot binding

最初に実装・review・fixed HEAD化する。

受入対象はpilot起動そのものではなく、

* launcher contract
* binding schema
* fresh/resume generation
* profile/guard/broker/provider pin
* invalid/stale binding拒否

までとする。

### G4-B — minimal broker adapter

G4-A fixed HEADを入力にして実装する。

G3 5 operation以外を公開しないことをformal reviewする。

### G4-C — independent collector

G4-A fixed HEADを入力に実装する。

G4-B内部logへ依存していないことをformal reviewする。

G4-BとG4-Cは設計上並行可能である。

### G4 integration acceptance

3 PRのfixed HEADを固定した後に初めて、

* native CLI
* fresh
* resume
* receive/delegate/collect-result/issue-record/observe-owner
* identity isolation
* F1〜F5
* current PM無変更

を統合して受入する。

その後も、pilot開始は別の明示判断とする。

## 13. G4開始可否

G1、G2、G3が同一provider commit

```text
0b2117c5f91f7950cc196e52edb188748adfa50a
```

を指しているという前提がPM側で既に対照済みであるため、G1〜G3のdependency gateは満たされている。

本書の7論点を設計決定として受入した後は、

**G4-A native launcher / binding PRから着手可**

と判断する。

ただし、

**G4-A着手可 ≠ pilot起動可**

である。

pilot起動はG4-A/B/C mergeおよび後続integration/fault acceptance完了後にも、別の明示的な開始判断を必要とする。
