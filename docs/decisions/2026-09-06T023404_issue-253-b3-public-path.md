# B3公開送受信経路の互換性対照

## 判断対象

P2のMonitor/受信/委譲/返信が公式公開経路で必要な引渡し保証を満たせるかを対照で決める。
上流PR #372待ちもB3全面移植も先決しない。
設計producerはagmsg_architect_codex、実装は別依頼後のagmsg_programmer_codex、独立実測は既存agmsg_verifier_codex、formal reviewerはagmsg_reviewer_claude。
実装・live配送・上流投稿は本書の範囲外である。

## 確認した差と不足

公式cutoffのsend.shはstorage_sendのID出力を捨て、宛先の表示だけを返す。
公式inbox.shは表示対象IDだけをmark-readするが、mark-read失敗をstderrへ報告してexit0を維持する。
forkのwatch.shはlib/claims.shに依存する。
閉鎖済み#37はqueued/claimed/handed_off/unknownを分離し、ACKを業務完了と扱わない契約である。
tests/test_claims.batsは排他owner、release後reclaim、他ownerのack拒否、期限切れ、選択ID、改行tab、team/receiver分離の7観点を持つ。
確認方法は固定Git objectの直接読取、#37のGitHub本文取得。実試験の再実行はしていない。

現brokerのaccepted/markerは模擬処理であり、B3参照0件を非依存証明に使わない。
公式api.sh messagesの履歴IDは送信結果照合の候補であるが、本文一致で最新IDを選ぶ方法は並行送信を区別できない。
一意requestIdを含む試験payloadと全対象履歴の完全性で照合できるかを検証し、不明時はunknownを返す。
requestIdはアプリ要求の相関IDであり、agmsg message IDや配送ACKの代用品ではない。

## 比較する2経路

| 経路 | 用途 | 合格で主張できる範囲 |
| --- | --- | --- |
| F: 現fork正式send/watch/claim/ack | 既存#37の意味論の対照 | 現forkの保持挙動。公式提供とは呼ばない |
| O: 公式send/inbox/api messages/正式Monitor | 提供済み公開入口だけの候補 | 実際に通った範囲のみ。私設ackやshadow leaseを作らない |

両経路を別install/root/DBの隔離fixtureで試し、同じlive DBに接続しない。
試験harnessは本番helperを実行し、観測用stubは失敗注入点と結果captureに限定する。
forkのSQL assertionは参照対照に残してよいが、公式consumerの実装がSQLを読む方式にはしない。

## 状態とack責任

送信要求受付、保存message ID確認、receiver予約、hostへの引渡し、protocol ACK、業務返信は別々に記録する。
Monitor stdoutに出たこと、inbox exit0、read_at、agentの業務完了を同一視しない。
送信側はmessage ID不明を成功済み配送として返さず、受信側はACK失敗・中断後の結果をunknownとして報告する。
業務返信は元requestIdと受信message IDを持ち、後続Issue記録はその返信を参照する。
未達・重複・不明の回復方針は試験結果で確定し、無条件再送しない。

| 対照 | 必要な観測・失敗条件 |
| --- | --- |
| 正常1周 | 送信ID→受信ID→委譲ID→返信ID→記録URLが結び付く |
| 同一本文の並行送信 | requestId別のmessage IDを維持。最新1件や本文一致だけの照合は失敗 |
| 受信前停止 | handed_offを報告しない。再開後に同じ未処理IDを回復 |
| stdout引渡しとACKの間で中断 | 実際の責任境界と再配送を記録。exit0をACK成功にしない |
| mark-read失敗 | stderr/状態不明を取りこぼさず、影ACKで成功を作らない |
| 同一宛先の並行receiver | 同一IDの二重引渡しを検出。原子的排他がなければ非互換 |
| release/期限切れ/別owner ACK | #37の期待値と比較。公式にない操作は未対応と記録 |
| 同SID別PID・resume | 旧receiverと新receiverのID/責任を混同しない |
| team・宛先・改行tab | scope漏れとpayload破損を検出 |
| 取得途中打切り/履歴欠落 | 完全照合を名乗らずunknown |

負の変異はID省略、最新行だけ採用、ACK失敗のexit0を成功化、二重receiverの片方を観測から除外するものを含める。
同じmarkerが増えたという集計だけでなく、IDごとの重複/欠落を示す。

## 判定と次工程

全必須対照がO経路で通れば、その限定公開経路をB3非依存として採用候補にする。
不足する場合は失敗した能力だけを提供側最小拡張の要求へまとめ、breakerへ返す。
候補は送信ID返却、引渡し結果とack失敗の機械可読化、必要ならreceiver排他であり、現時点で全部追加すると決めない。
不明を保った限定運用を選ぶ場合も、#37の保証を弱める変更としてbreaker判断を経る。
公式側へ私設schema reader、影claim/ack、恒久fork fallbackを置かない。

reportはvalue/cutoff/source/command、ID対応、故障注入点、期待/実値、unknown範囲を記録する。
READMEは対照設計だけなら無変更。公開契約の追加が必要と決まった場合、その実装PRで利用方法・結果状態を更新する。
P2実接続着手には採用設計、公式B1/B2提供版、B3採用経路、提供側独立対照、consumer試験計画の固定とreviewer受入が必要。
consumer統合結果は実装後・pilot起動前に要求する。設計段階へ循環させない。
