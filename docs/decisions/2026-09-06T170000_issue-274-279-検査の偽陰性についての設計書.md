# 検査が「検出できなかった」を「問題なし」として通す 2 件（Issue #274 / #279）

## 0. PR 構成の宣言

**2 本に分ける。**

| PR | 主張 | 触るファイル |
| --- | --- | --- |
| PR-A（#274） | 観測窓に入らなかったことを、事象が起きなかったことと区別する | `scripts/issue253_actas.py`、`tests/test_issue253_actas.py`、`tests/issue253_mutations.py` |

**共通の機構では直せない。** 症状は同じ型（検査の偽陰性）だが、
一方は Python の戻り値を捨てている呼び出し側の欠陥、

`agent-role.rule.md`「1 PR = 1 主張」に従い分割する。

**依存関係は無い。** どちらを先にマージしてもよい。

## 1. Issue #274 — `wait_for` のタイムアウトを判別可能にする

### 1.1 現状（実測）

`wait_for` は**既にタイムアウトを bool で返している。**

```python
# scripts/issue253_public_path.py:151
def wait_for(predicate, seconds=8):
    deadline = time.monotonic() + seconds
    while time.monotonic() < deadline:
        if predicate():
            return True
        time.sleep(0.05)
    return False
```

**欠陥は呼び出し側にある。** 全 8 箇所のうち、戻り値を捨てているのは 2 箇所だけである。

| 呼び出し元 | 戻り値 |
| --- | --- |
| `issue253_public_path.py` の 6 箇所（214/225/314/316/318/335 行） | **すべて受けている** |
| **`issue253_actas.py:79`** | **捨てている** |
| **`issue253_actas.py:84`** | **捨てている** |

つまり**本件は「`wait_for` の設計が悪い」のではなく、「同じファイル群の中で確立している作法から
2 箇所だけ外れている」**という形である。

### 1.2 既に確立している作法

`issue253_public_path.py:314-343` が正本である。

```python
ready   = wait_for(lambda: all(... watch-poll ...))
reached = wait_for(lambda: any(request in ... for h in handles))
...
results["watch_" + mode] = {
    "status": receiver_verdict(...) if ready and reached and ... else "unknown",
    ...
    "observation_reached": reached,
    "all_receivers_polled_before_send": ready,
}
```

**2 つのことを同時にやっている。**

1. **判定の格下げ**: 観測窓に入らなかったら `"unknown"` にする（`"incompatible"` や `"pass"` にしない）
2. **証跡の保存**: どちらの待ちが外れたかを報告へ残す

**#274 の受入条件は、この作法を `issue253_actas.py` へ適用すれば満たされる。**
新しい機構を足す必要は無い。**timeout 値には一切触れない。**

### 1.3 設計

#### 1.3.1 観測結果を受ける

```python
polled  = wait_for(lambda: all((root / f"tmp/poll.{i['host_pid']}").exists()
                               or h[0].poll() is not None for i, h in watches), seconds=10)
item = f.send("actas-same" if same_sid else "actas-different")
observed = wait_for(lambda: any(item[0] in Path(str(h[2]) + ".stdout").read_text()
                                for _, h in watches), seconds=5)
```

**`seconds` は現状のまま（10 / 5）**。値を上げない。

#### 1.3.2 判定へ反映する

`evaluate()` に観測の成否を渡し、**入らなかったら `"unknown"` を返す。**

```python
def evaluate(instances, correlation, polled=True, observed=True):
    if not polled or not observed:
        return "unknown"          # 観測窓に入らなかった。事象の有無は言えない
    ...                           # 以降は現状のまま
```

**既定値を `True` にするのは、既存の試験（`tests/test_issue253_actas.py`）が
2 引数で呼んでいるためである。** 既定値により、それらは意味を変えずに通り続ける。

> **ここは意図的な設計判断である。** 既定 `True` は「観測できた」に倒すので、
> **呼び忘れると fail-open になる。** これを許すのは、
> §1.3.4 の検査が「呼び忘れ」自体を落とすためである。
> **検査を入れないなら既定値を置いてはならない。**

#### 1.3.3 証跡を残す

`observe()` の戻り値へ 2 つの真偽値を足す。

```python
return {"role_ownership": ownership(instances),
        "role_path": evaluate(instances, correlation, polled, observed),
        "watch_poll_reached": polled,          # 追加
        "handoff_observation_reached": observed,  # 追加
        ...}
```

**`role_ownership` は格下げしない。** これは claim の応答だけから決まり、
watch の観測窓とは独立だからである。**格下げの範囲を広げすぎない。**

#### 1.3.4 再発を止める検査

**同じ誤りが次の呼び出しで再発しうる。** 戻り値を捨てても Python は何も言わない。

`tests/test_issue253_actas.py` へ、**ソースを走査して `wait_for(` の戻り値が
捨てられていないことを確かめる試験**を足す。

```python
def test_no_wait_for_result_is_discarded(self):
    for path in (SCRIPTS / "issue253_actas.py", SCRIPTS / "issue253_public_path.py"):
        tree = ast.parse(path.read_text())
        for node in ast.walk(tree):
            if isinstance(node, ast.Expr) and isinstance(node.value, ast.Call) \
               and getattr(node.value.func, "id", None) == "wait_for":
                self.fail(f"{path.name}:{node.lineno}: wait_for result discarded")
```

**`ast` を使う。`grep` ではない。** 文字列一致だと、コメントや文字列リテラル中の
`wait_for(` を拾い、逆に複数行に折り返した呼び出しを見落とす。

**`ast.Expr` は「式文」、つまり値を捨てている呼び出しである。**
代入・条件式・引数としての使用はこれに当たらない。

### 1.4 実測（負の対照）

**実装時に、下記 4 件を必ず実行して結果を記録すること。** 本設計書の時点では未実施である
（設計のみのため）。

| # | 種別 | 変異 | 期待 |
| --- | --- | --- | --- |
| 1 | 正の対照 | 変更なし | 既存の `tests/test_issue253_actas.py` が PASS |
| 2 | 負の対照 | `evaluate` の `if not polled or not observed:` を削除 | **新設の試験が FAIL** |
| 3 | 負の対照 | `observed = wait_for(...)` を `wait_for(...)` へ戻す | **§1.3.4 の走査試験が FAIL** |
| 4 | 負の対照 | `polled` を常に `True` にする | **新設の試験が FAIL** |

**判定は三値で報告する**（`development.rule.md`）。
`KILLED` / `KILLED-BY-TSC`（Python では import エラー等）/ `SURVIVED` を区別する。

**#3 は §1.3.4 の検査そのものへの負の対照である。** 検査を書いたら、
在ると分かっている違反を 1 件掛けて、検出できることを確かめる。

### 1.5 やらないこと

- **`seconds` の値を変えない。** 受入条件が明示的に禁じている
- **`wait_for` を例外送出へ変えない。** 6 箇所の正しい呼び出し側を書き換えることになり、
  変更の範囲が本件の主張を超える。`issue253_public_path.py` 側は既に正しく動いている
- **`ownership()` の判定を変えない**（§1.3.3）

## 2. Issue #279 — 非アンダースコア名の未定義呼び出し

### 2.1 まず、これは本当に素通りするのか（実測）

**素通りする。しかも実行時にも落ちない。**

`cleanup_windows_native_processes` の本体へ `zqx_no_underscore_fn "$1"` を挿入し、
`build_case` で生成して `bash` で実行した。

```
GEN: succeeded (gate did NOT catch)
RUN rc= 0
stderr tail: ['bash: line 3: zqx_no_underscore_fn: command not found']
POS-CTRL rc= 0 stderr: (empty)
```

**`rc=0` である。** `command not found` は stderr へ出るが、
その後の文が成功して関数が 0 を返すため、**終了コードには現れない。**

**したがって「ゲートが緩くても、実行時に rc=127 で落ちるから気づける」は成り立たない。**
Issue #275 が rc=127 で顕在化したのは、**たまたま失敗が関数の戻り値に伝わる位置にあった**ためである。

**stderr を比較する試験だけが検出できる。** 検出は試験の書き方に依存しており、
**ゲートが唯一の構造的な防御である。**

> **正の対照**: 同じ手順で未改変の fixture を生成・実行し、`rc=0` / stderr 空を確認した
> （上記 `POS-CTRL`）。**「常に rc=0 を返すだけの実験」ではない**ことをこれで区別している。

### 2.2 案 1（正規表現の緩和）は、そのままでは成立しない

Issue が挙げる方向 1（`HELPER` を `[A-Za-z_]...` へ緩める）を実測した。

| 段階 | 残る誤検出 |
| --- | --- |
| 素朴に緩めるだけ | **33〜34 件** |
| ＋ヒアドキュメント本体とコメントを除外 | **12 件** |
| ＋引用符の中身・`case` パターンを除外 | **1〜3 件**（`INFO` / `attempts` / `start`） |

素朴に緩めた時点の残骸（抜粋）:

```
Command, Creation, ForEach, Get, INFO, Name, Pid, Ppid, Where, Write,
awk, case, continue, do, done, elif, else, empty, esac, exit, fi, for,
foreach, if, its, local, printf, process, return, then, tr, true, try, while
```

**bash のキーワード、PowerShell のコマンドレット、`case` のパターン、
そして英文コメント中の単語（`its` / `process` / `empty`）が混ざっている。**

原因は fixture の構造にある。

- PowerShell が**複数行にまたがる単一引用符の文字列**として埋め込まれている（600-660 行）
- `''|INFO:*|*No\ tasks*) state=gone ;;` のような**`case` の選択肢**がある（567 行、852 行）

`lifetime_case.py` のコメントが「プロトタイプが引用の扱いを誤った」と書いているのは、
**まさにこの構造を指している。**

**マスク処理を重ねれば 1〜3 件まで落ちるが、0 にはならなかった。**
残りを消すには `case` の選択肢の中の `|` 区切りや行継続まで扱う必要があり、
**それは shell の字句解析器を書くことにほかならない。**

**設計判断: 案 1 は採らない。** 誤検出が残る検査は、
**「またあの誤検出か」で無視されるようになり、検査として死ぬ。**

### 2.3 採る案 — 規約を「仮定」から「強制」へ変える

**現状の `HELPER` 正規表現は「このリポジトリのヘルパは常に `_[a-z]...`」という
仮定の上に立っている。fixture 側にはその仮定を破る定義が 13 件実在する。**

**仮定を検査で強制すれば、仮定は事実になる。**

#### 2.3.1 fixture 側の改名

`tests/test_codex_bridge_launcher.bats` の非規約名 13 件を分類する。

| 分類 | 名前 | 扱い |
| --- | --- | --- |
| **bats のライフサイクル** | `setup`, `teardown` | **改名しない。** bats が名前で呼ぶ |
| **外部コマンドの意図的な差し替え** | `taskkill` | **改名しない。** 実コマンドを隠すことが目的 |
| **通常のヘルパ** | `_937_start_token`※, `cleanup`, `cleanup_windows_native_processes`, `count_child_launchers`, `put_record`, `record_windows_native_events`, `run_launcher`, `wait_for_child_count`, `windows_native_diagnostics`, `write_request` | **`_` 接頭辞へ改名する** |

※ `_937_start_token` は `_` で始まるが `_[a-z]` に一致しない（次が数字）。
**規約側を `_[a-z0-9][a-z0-9_]*` へ広げるか、名前を変えるかの判断が要る。**
**設計としては名前を変える**（規約を広げると、規約が名前に合わせて動く前例になる）。

`cleanup_windows_native_processes` は `tests/windows/test_lifetime_adapter.py:56` が
**entry 名として直接参照している。** 改名時は同時に直す。

#### 2.3.2 規約を検査する

`tests/windows/lifetime_case.py` へ、**fixture 内の定義名が規約に従うことを確かめる関数**を足す。

```python
SHADOWED = frozenset({'setup', 'teardown', 'taskkill'})
"""Names that must NOT be renamed: bats lifecycle hooks and deliberate command shadows."""

def nonconforming_definitions(source):
    """Fixture-defined names that break the `_[a-z]` convention the HELPER scan assumes."""
    return {n for n in definition_names(source)
            if n not in SHADOWED and not re.fullmatch(r'_[a-z][a-z0-9_]*', n)}
```

`build_case` の冒頭で呼び、非空なら `UnresolvedReference` を送出する。

**`SHADOWED` は手書きの一覧である。** §2.5 で、なぜこれが
Issue #275 が禁じた「収録一覧」と違うのかを述べる。

#### 2.3.3 何が防げて、何が防げないか

| 入力 | 変更後 |
| --- | --- |
| `_typo_helper` を呼ぶ（未定義） | **検出する**（現状も検出する） |
| `zqx_no_underscore_fn` を呼ぶ（未定義） | **検出しない** |
| 非規約名のヘルパを fixture へ**新設**する | **検出する**（これが新しい防御） |

**「非規約名の未定義呼び出しそのもの」は依然として検出できない。**
外部コマンドの呼び出しと区別できないためである（§2.2）。

**しかし Issue #279 が心配している事象** —
「将来、規約外の名前のヘルパを entry から呼ぶようになった時点でゲートが素通りする」 —
**は防げる。** そのヘルパを fixture へ定義した時点で `build_case` が落ちるからである。

**穴を塞ぐのではなく、穴へ至る道を塞ぐ。**

### 2.4 案 3 単独（改名だけ）を採らない理由

改名だけでは、**次に誰かが非規約名を足したときに元へ戻る。**
`development.rule.md` の言い方をすれば、**運用で回すことになり、抜けたら気づけない。**
**検査（§2.3.2）と対で入れる。**

### 2.5 `SHADOWED` は Issue #275 が禁じた「一覧」と何が違うか

Issue #275 の設計は「**どのヘルパを収録するかの一覧を持たない**」ことを受入条件にした。
`SHADOWED` は一覧である。**矛盾しないか。**

**しない。性質が違う。**

| | #275 が禁じた一覧 | `SHADOWED` |
| --- | --- | --- |
| 中身 | **収録すべきヘルパ**（参照関係から導出できる） | **改名してはならない理由がある名前** |
| 導出可能か | **できる**（だから一覧は冗長で、腐る） | **できない**（bats の仕様と、外部コマンドを隠す意図） |
| 漏れたときに起きること | 静かに未収録になり rc=127 | **検査が落ちる**（fail-closed） |

**導出できないものだけを宣言する。** 導出できるものは導出する。

**`SHADOWED` に漏れがあれば `build_case` が落ちるので、漏れは静かに通らない。**

### 2.6 実測（負の対照）

**実装時に下記を実行して記録すること。**

| # | 種別 | 変異 | 期待 |
| --- | --- | --- | --- |
| 1 | 正の対照 | 改名後、変更なし | `test_lifetime_case.py` / `test_lifetime_adapter.py` が PASS |
| 2 | 負の対照 | fixture へ `qqzz_bad_name() { :; }` を足す | **`UnresolvedReference` で KILLED** |
| 3 | 負の対照 | `SHADOWED` から `taskkill` を除く | **KILLED**（検査が生きている証拠） |
| 4 | 負の対照 | `nonconforming_definitions` の呼び出しを消す | **#2 の試験が FAIL** |
| 5 | **非警報対照** | `setup` / `teardown` / `taskkill` を残したまま | **落ちない**（`NO-ALARM`。`SURVIVED` と書かない） |

**#5 を `SURVIVED` と書かないこと。** 良い結果と悪い結果へ同じ語を使わない
（`development.rule.md`）。

**#2 の名前は、この設計書に書いた語をそのまま使わないこと。**
番兵の語が検査対象へ混入する型を踏む（`development.rule.md`「型 1」）。
**実装時にその場で別の語を作る。**

### 2.7 やらないこと

- **`HELPER` 正規表現を緩めない**（§2.2 の実測による）
- **シェルの字句解析器を書かない**
- **`bash -n` 以外の実行を生成時に足さない。** 任意の entry を実行すると副作用がある
