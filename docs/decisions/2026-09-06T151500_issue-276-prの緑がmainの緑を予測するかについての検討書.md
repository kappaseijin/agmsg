# PR の緑は main の緑を予測するか（Issue #276）

## 0. 答え

**予測しない。**

`pull_request` の CI が検査するのは「head を **base の当時のスナップショット** へマージしたもの」
であり、**実行時点の `main` ではない**。両者は、PR に対する最後のイベント以降に `main` が
進んだ分だけ食い違う。

**外れる条件は 1 つに書ける。**

> **PR に対する最後のイベント（head への push、base の変更、PR の作成）より後に
> `main` が進み、その後で CI が走った場合。**

このとき CI は古い base で検査し、**緑は「その古い base では壊れない」ことしか意味しない。**

#266 はこの条件に**ちょうど 60 秒差で**当たっていた（§2）。

## 2. 機構

`refs/pull/N/merge` は GitHub が**PR のイベントを契機に計算して保持する ref** である。

**`base` ブランチへの push では再計算されない。**

```
PR イベント（head push / base 変更 / PR 作成）
        ↓ ここで merge ref を計算
refs/pull/N/merge = merge(head, base_at_that_moment)
        ↓
main が進む                    ← merge ref は追随しない
        ↓
CI が走る                      ← 古い merge ref をチェックアウト
```

`actions/checkout@v4` は `pull_request` で `refs/remotes/pull/N/merge` を取る（§1.1 のログ）。
**したがって CI の検査対象は、PR の最後のイベント時点の base で固定される。**

### 2.1 なぜ #266 だけが当たったか

**本日の他の PR run は、いずれも当時の main 先端をマージしていた。**

| run | 開始 (UTC) | マージ先 base | 当時の main 先端 | 判定 |
| --- | --- | --- | --- | --- |
| 34001650900 | 00:34:39 | `a597e63b` | `a597e63b` | 一致 |
| 34001827692 | 00:38:42 | `a597e63b` | `a597e63b` | 一致 |
| 34002405408 | 00:52:05 | `a597e63b` | `a597e63b` | 一致 |
| 34005714630 | 02:59:39 | `e8345f9d` | `e8345f9d` | 一致 |
| **34008357842（#266）** | **03:11:11** | **`e8345f9d`** | **`69573a8`** | **不一致** |
| 34012262102 | 04:44:23 | `496f650e` | `496f650e` | 一致 |
| 34013831711 | 05:22:44 | `0f21945d` | `0f21945d` | 一致 |

**差は「PR の最後のイベントから CI 実行までの間に main が進んだか」だけである。**

通常は head へ push した直後に CI が走るため、両者はほぼ同時刻で一致する。
#266 は **base 変更で merge ref が確定した 64 秒後に main が進み、その 7 分後に CI が走った。**

### 2.2 再実行（attempt 2）は原因ではない

疑った経路だが、**否定された。**

- attempt 1（03:11:11）: `bats (ubuntu-latest 3/4)` と集約ジョブ `bats` が **FAILURE**
- attempt 2（03:40:30、失敗ジョブのみ再実行）: 全緑
- **`Windows offline lifetime semantics` は attempt 1 の時点で SUCCESS**（再実行されていない）

main を壊した Windows ジョブは、**最初から緑だった。**
再実行が隠したのは別のジョブである。**再実行を禁止しても本件は防げない。**

## 3. 負の対照

breaker の依頼にある「同じ形の PR を意図的に作り、CI が落ちるか確かめる」について、
**本機構の下では、この対照は 2 本に分かれる。**

| 腕 | 条件 | 予測 |
| --- | --- | --- |
| A | merge ref が**新しい**（base 進行後に PR イベントがある） | **赤になる**（検出できる） |
| B | merge ref が**古い**（base 進行後に PR イベントが無い） | **緑になる**（#266 の再現） |

**腕 A は実地の観測で満たされている。** §2.1 の 6 本はいずれも当時の main 先端をマージしており、
`main` の内容に依存する破綻があれば検出できる位置にあった。

**腕 B を実験で再現するには `main` を進める必要がある**（base が進まないと条件が成立しない）。
`main` への merge を伴うため、**本調査では実施していない。**
代わりに §1.1 の生ログで「古い base をチェックアウトした」ことを直接観測しており、
**腕 B は推定ではなく観測済みである。**

### 3.1 検査自身の妥当性

`Merge X into Y` 行を根拠にしているため、**この行が取れない場合に偽の結論を出しうる。**
正の対照として、**同じ抽出を 7 本の run に掛けて全件で行が取れること**を確認した（§2.1 の表）。
1 本だけ取れて他が空、という状態ではない。

## 4. 付随して判明したこと（本問とは別）

**`main` にブランチ保護もルールセットも掛かっていない。**

```
GET repos/kappaseijin/agmsg/branches/main  ->  {"name":"main","protected":false}
GET repos/kappaseijin/agmsg/rulesets       ->  []
```

`.github/workflows/tests.yml` の冒頭コメントは
`bats (ubuntu-latest)` / `bats (macos-latest)` を「**REQUIRED status checks on main**」と
書いているが、**GitHub 側にその設定は存在しない。**

**限界**: 使用したトークンは `admin:false` のため、保護設定の詳細を読む権限が無い。
ただし `branches/main` の `protected` は公開フィールドであり、`false` を返している。
**`rulesets` が空であることと合わせて「保護なし」と判断した。**

これは Issue #276 の問いの範囲外だが、**§5 の案 2 が前提とする設定が現に無い**ため記録する。

## 5. merge 基準の見直し案

**決定はユーザーが行う。以下は選択肢と影響の提示である。**

### 案 1: 「base が進んだら approve を無効とする」を運用規約に入れる（追加設定なし）

merge の直前に、**CI が実際にチェックアウトした base** と現在の `main` を突き合わせる。

```bash
# CI が使った base（run の任意のジョブのログから）
gh run view --repo <repo> --job <job_id> --log | grep -oE 'Merge [0-9a-f]{40} into [0-9a-f]{40}'
# 現在の main
git rev-parse origin/main
```

不一致なら **head へ空コミットを push して CI を取り直す**（merge ref が再計算される）。

- **利点**: 今すぐできる。GitHub の設定変更が要らない
- **欠点**: 人手の照合であり、抜けたら気づけない。`git.rule.md` の
  `--match-head-commit`（head の固定）は**base の鮮度を守らない**

### 案 2: ブランチ保護で「Require branches to be up to date before merging」を有効にする

GitHub が「base が進んだ PR」を merge 不可にし、更新を強制する。

- **利点**: 仕組みで防ぐ。人手の照合が要らない
- **欠点**: **`main` に保護設定が現在存在しない**（§4）。保護の新設が要る。
  admin 権限が要るため、**ユーザー本人の操作が必要**。
  また PR ごとに base 追随の push が要り、その都度 approve を取り直すことになる

### 案 3: merge queue を使う

GitHub が merge 直前に「main + PR」で CI を走らせてから入れる。

- **利点**: 本問を構造的に消す。base の鮮度を人が見なくてよい
- **欠点**: 保護設定と `merge_group` イベントの追加が要る。CI の実行回数が増える

### 案 4: 何もせず、事実だけを記録する

「PR の緑は main の緑を保証しない」を前提として運用し、**main が赤くなったら直す**。

- **利点**: 追加コストが無い
- **欠点**: 本日の損失（main が壊れた状態が 1 時間以上続いた）がそのまま再発しうる

## 6. 確認できていないこと

- **GitHub が merge ref を再計算する契機の完全な一覧**。観測したのは
  「base 変更時に計算され、その後の base への push では再計算されない」ことだけである。
  公式の仕様文書には当たっていない
- **腕 B の能動的な再現**（§3）。`main` を進める必要があるため実施していない
- **`main` の保護設定の詳細**。トークンが `admin:false` のため読めない（§4）
- **他リポジトリでも同じか**。本調査は `kappaseijin/agmsg` の実測のみ
