# Issue #236 fork-local P2 G1〜G3分割

## 決定

P2接続実装の前提を、三つの独立Issueに分ける。

G1はfork-local providerの固定commitとB1/B2対照を受入する。

G3はP2 consumerが必要とする操作、宛先、payload、失敗状態を固定する。

G2はG3で選ばれたB3 capabilityだけをprovider契約と対照へ落とす。

番号順ではなく、依存順は**G1とG3を並行可、G2はG3後、P2接続実装はG1/G2/G3後**とする。

B3をconsumerの要求より先に「全部必要」又は「不要」と決めないためである。

この文書はIssue分割の設計である。

provider commandの実装、B3実装、broker/adapter/collector、pilot起動は含まない。

G2はG3のoperation matrixなしに開始しない。

## 2. G1: provider pinとB1/B2対照

### 受入条件

1. manifestは`repository=kappaseijin/agmsg`、40桁commit、canonical provider root、schema versionを持つ。
2. consumer/fixtureが同一commitを読んだことを確認し、短縮SHA、別root、未到達commitを拒否する。
3. B1は`api.sh get teams <team> registrations --schema-version 1`だけを利用し、複数tuple、重複tuple、破損、競合で既存の完全性/unknown対照を通す。
4. B2は`api.sh get teams <team> actas-owner <agent> --schema-version 1`だけを利用し、`owned`、`stale`、`absent`、`not_found`、`unknown`を混同しない。
5. config、runtime、claim、session、processのread-only前後比較が0である。
6. artifactはprovider commit、manifest digest、正負対照、実行command、review対象HEADを結び付ける。

### 除外

- B3 capability又はP2 adapterの実装
- `fujibee/agmsg`への適用又は採用確認
- live team/claimへの接続

## 3. G3: consumer契約

G3はproviderが何を提供すべきかを先に限定する設計Issueである。

consumerはPM pilotの限定操作だけを列挙し、現PMの全権限を再現しない。

| operation | actor / target | 成功の証拠 | failure時 |
| --- | --- | --- | --- |
| receive | pilot宛の未処理message | immutable message ID、recipient、受信状態 | unknownなら未読を既読化せず停止 |
| delegate | pilotから事前登録worker | request ID、delegate message ID、固定payload schema | 宛先/field不一致を拒否 |
| collect-result | workerからpilot | request IDとresult message IDの対応 | ID未対応を成功にしない |
| issue-record | pilotから検証用Issueだけ | 再取得済みcomment URLと実改行本文 | write結果不明なら自動再送しない |
| observe-owner | pilot seatだけ | B2のopaque owner/state | `unknown`をfree/許可へ変換しない |

### 受入条件

1. 各operationの入力schema、最大長、actor、宛先、Issue scope、成功/失敗/unknownを一意に定義する。
2. `send`、`inbox`、`history`、`handoff receipt`、`claim/release/ack`のうち必要なB3 capabilityを明示し、不要なcapabilityを空欄でなく`not-used`として記す。
3. claim/release/ackを`not-used`にするなら、consumer固定HEADで該当private command/schema参照が0件となる検査を設計する。
4. 直接Bash、内部SQLite/claim/roster読取、任意root/wrapper、対象外Issue/宛先を拒否する負の対照を持つ。
5. G3の受入はconsumer計画だけであり、provider実装又はpilot成功を意味しない。

## 4. G2: 選択済みB3 capability

G2はG3のmanifestを入力にする。

manifestに無いcapabilityを「既存B3だから」として使用しない。

### 受入条件

1. capabilityごとに公開command、固定argv、JSON schema、exit status、message/request/receipt IDの対応を固定する。
2. team、recipient、owner、message IDのscopeを失わず、同一ID再送、別owner、途中失敗、history不足、unknownを区別する。
3. capabilityが未提供、schema不一致、ID対応不能、read failure、競合なら非0又は明示unknownで停止する。
4. 正の対照と、未宣言操作・別recipient・IDすり替え・unknown成功化の変異を各capabilityで分けてKILLする。
5. G1のprovider commitと一致しない結果を受入しない。

### 除外

- B3全機構の移植
- Issue #253の再オープン
- P2 adapterがまだ使わないlease/ack capability

## 5. G4へのhandoff

G4の起点依頼には、G1/G2/G3のPR URL、各fixed HEAD、provider commit、manifest digest、
accepted capability一覧、未使用capabilityの参照0件対照、consumer test planを添付する。

一つでも取得不能、HEAD不一致、unknown、又は未受入ならG4を開始しない。

G4の実装はnative launcher、最小broker adapter、独立collectorを別々のPRに分ける。

G4のmergeだけではpilotを起動しない。

## 6. #236とG0

#236はG1〜G3の完了だけでCLOSEDにしない。

G4の固定HEAD受入、専用pilotのfresh/resume・委譲周回・故障復旧・現PM無変更の受入までOPENを維持する。

P3（現PM交代）とP4（横展開）は#236のP2完了後に別Issueとして切り出す。

`agguild`/`agguild_pool`新設と物理移行は、Issue #373のG0が全件CLOSED又は明示NOT_PLANNEDになるまで開始しない。

README影響はない。
