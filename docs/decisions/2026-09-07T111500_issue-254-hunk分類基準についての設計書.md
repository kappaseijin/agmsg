# hunk の分類基準（Issue #254）

## 0. 要旨

**マージ済みの設計書には `owner` の決め方が書かれていなかった。本書がそれを定める。**

**734 hunk のうち、機械的に決まるのは 294、判断が要るのは 440 である**（§2）。

**「機械的」とは、規則を読めば同じ答えになり、実行者によって割れないことを指す。**
**分類の正しさは網羅検査では守れないので、標本の再分類で検算する**（§5）。

---

## 1. `owner` の判定規則

**上から順に見て、最初に当たったものを採る。** 当たらなければ `unclassified` のまま残す。

```
1  exception   移せない事情がある
                 ・その repository でしか意味を持たない設定
                 ・上流と fork の双方が触っており、分離すると壊れる
2  pool        エージェントの人格・状態などの「データ」
3  official    上流の挙動の修正・改善であり、fork 固有の概念に依存しない
4  agguild     fork 固有のエージェント運用の概念を実装している
```

**`official` を `agguild` より先に見る。** 逆にすると、上流へ返せるものが
「fork のものだから」と手元に残る。**上流へ返せるものを先に拾う。**

### 1.1 `pool` はこの台帳では 0 件の見込みである

**`agguild_pool` はエージェントの人格・状態の置き場である**（Issue #222）。
**それらは `codex_monitor_agents` にあり、本 repository には無い。**

**したがって本台帳に `pool` は現れないはずである。**
**現れたら、それは分類の誤りか、私の想定違いである。** どちらにせよ止めて確認する。

**「0 件のはず」を検査に入れる**（§5.4）。

### 1.2 `disposition` は `owner` から従属的に決まる

| `owner` | `disposition` | 意味 |
| --- | --- | --- |
| `official` | `adopt` | 上流へ提案する |
| `agguild` | `port` | agguild へ移す |
| `exception` | `port` または `drop` | **ここだけ判断が要る** |
| — | `drop` | 移さず捨てる。**理由が要る** |

**`official` なのに `drop`、`agguild` なのに `adopt` は不整合である。**
**検査で落とす**（§5.4）。

## 2. 機械的に決まる分と、判断が要る分

**実測に基づく内訳である。合計は 734 に一致する。**

| 区分 | hunk | 決め方 |
| --- | --- | --- |
| **`docs/decisions` `docs/superpowers` `docs/plan` `docs/adr`** | **83** | **機械的**（§3.1） |
| `docs/actas.md` / `docs/building-on-agmsg.md` | 9 | 判断 |
| **`tests/` のうち実装と名前が対応するもの** | **211** | **機械的**（§3.2） |
| `tests/` のうち対応が無いもの | 83 | 判断 |
| `tests/fixtures/**` `tests/test_helper.bash` 等 | 29 | §3.3 |
| `scripts/` | 264 | 判断 |
| 直下（`README.md` 21 / `README.ja.md` 12 / `install.sh` 11 / `uninstall.sh` 4 / `SKILL.md` 3） | 51 | 判断 |
| `app/` 2 / `.github/` 2 | 4 | 判断 |

```
機械的  294   判断が要る  440
```

**判断が要るほうが多い。** 「worker へ 734 行を渡す」という形では進まない。

### 2.1 「機械的」と「すぐ埋まる」は別である

**機械的な 294 のうち、生成直後に埋まるのは 83 だけである。**

| 区分 | hunk | いつ埋まるか |
| --- | --- | --- |
| `docs/` の 4 ディレクトリ | **83** | **生成直後**。他に依存しない |
| `tests/` の対応あり | **211** | **対応する実装が分類されてから**（§3.2） |
| 判断が要る | 440 | 便ごとに |

**`tests/` の 211 は規則で決まるが、規則の入力（対応する実装の `owner`）が
判断の結果である。** したがって**判断より先には埋まらない。**

**`--gate` が最初に報告する未分類は 440 ではなく 651（440 + 211）である。**

```
生成直後        --gate は 651 行を報告
判断が進むにつれ  対応する試験が埋まり、651 -> ... -> 0 へ減る
```

**`--classify-mechanical` は何度でも実行できる形にする。**
**1 回で終わる処理ではない。**

> **初版は「機械的 294 / 判断 440」とだけ書き、埋まる順序に触れていなかった。**
> **`--classify-mechanical` の実装で、初回に埋まるのが 83 だけであることが分かった**
> （programmer の指摘、2026-09-07）。
> **「規則で決まる」ことと「いま決められる」ことを、私が区別していなかった。**

## 3. 機械的な規則

### 3.1 fork 自身の記録は `agguild`

```
docs/decisions/**  docs/superpowers/**  docs/plan/**  docs/adr/**   ->  owner=agguild
                                                                        disposition=port
```

**これらは fork の検討・計画・決定の記録であり、上流へ返す対象ではない。**

**例外**: `docs/actas.md` と `docs/building-on-agmsg.md` は**機能の説明**であり、
その機能が `official` なら文書も `official` になりうる。**判断へ回す。**

### 3.2 試験は、対応する実装の `owner` を継ぐ

**対象は `tests/` 配下で basename が `test_` で始まるファイルすべてである。**
**拡張子を問わない。`tests/` 直下に限らない。**

```
対象               tests/** のうち basename が "test_" で始まるもの
                   （.bats / .bash / .sh を問わない。tests/isolated/** も含む）
突き合わせる名前   basename から先頭の "test_" と拡張子を除いた部分
突き合わせ先       実装ファイルの basename から拡張子を除いた部分
正規化             "-" を "_" にし、小文字にする
対応の判定         完全一致、または一方が他方の接頭辞
実装の探索範囲     tests/ と docs/ を除く全パス（scripts/ だけではない）
```

**この 3 行（対象・拡張子・階層）を書かないと、読む人によって数が変わる。**
**実測した**（下記 §3.2.1）。

**探索範囲を `scripts/` に限ってはならない。** `install.sh` や `uninstall.sh` は直下にある。
**実測では、範囲を広げると対応が 42 ファイルから 44 ファイルへ増えた。**

**正規化を省いてもならない。** `codex-bridge.js` と `test_codex_bridge.bats` は
ハイフンとアンダースコアだけが違う。**正規化しないと 28 ファイルしか当たらない。**

| 突き合わせの条件 | 対応が取れたファイル |
| --- | --- |
| `scripts/` のみ・正規化なし | 28 |
| `scripts/` のみ・正規化あり | 42 |
| **全パス・正規化あり** | **44**（211 hunk） |

#### 3.2.1 対象範囲の読み違いで数が変わる（実測）

**初版は「`tests/test_<名前>.bats`」と書いていた。**
**その字面どおりに読むと `tests/` 直下の `.bats` だけになり、数が変わる。**

| 読み | 対応あり | 対応なし | その他 | 計 |
| --- | --- | --- | --- | --- |
| **A**: `tests/` 直下の `test_*.bats` のみ（初版の字面） | 43 / **210** | 22 / 60 | 53 | 323 |
| **B**: `tests/**` の `test_*` すべて（本書が採る） | 44 / **211** | 23 / 83 | 29 | 323 |

**区分が変わるのは 2 ファイルである**（verifier の指摘、2026-09-07）。

```
tests/isolated/test_pm_pretool_guard_real_cli.sh   A: その他  ->  B: 対応あり
tests/test_helper.bash                             A: その他  ->  B: 対応なし
```

**「対応あり」の数の差は 1 だが、区分が動くファイルは 2 である。**
**初版は前者だけを見て「差は 1 ファイル」と書いていた。**

**verifier は字面どおり A で読み、43 / 210 を得た。私は B で測っていた。**
**規則の字面と、私の測定が食い違っていた。**

**B を採る。** `tests/isolated/**` の試験も `tests/test_helper.bash` も試験であり、
**対応が取れるなら継ぐ、取れないなら判断へ回す、という扱いは同じでよいからである。**

**A では `tests/isolated/**` と `test_helper.bash` が「その他」へ落ち、
規則の適用対象から外れる。** それは意図していない。

**対応が取れなければ機械的には決まらない。** `unclassified` のまま判断へ回す（23 ファイル / 83 hunk）。

##### 候補が複数あるときは、割れたら判断へ回す

**対応が取れた 44 ファイルのうち、22 ファイル（166 hunk）は実装の候補が複数ある**（実測）。

```
候補が 1 つ    22 ファイル /  45 hunk
候補が複数     22 ファイル / 166 hunk
```

**規則は「対応する実装の owner を継ぐ」であって「どれかの owner を選ぶ」ではない。**

```
候補の owner がすべて同じ    その owner を継ぐ
候補の owner が割れている    継がない。判断へ回す（fail-closed）
```

**多数決を採らない。** 多数決は、答えが無いところに答えを作る。

**「最初の候補」も採らない。** 並び順に依存し、**並べ方を決めていない**
（§4.1 で同数の順序を決めなかったのと同じ誤りになる）。

##### 割れは 2 層ある。ファイル内の割れも同じ扱いにする（2026-09-07T12:30:00+09:00 追記）

**初版のこの節は「候補（＝実装ファイル）の owner」と書いた。**
**しかし `owner` は hunk ごとに決まる列であって、ファイルごとに決まる列ではない。**
**「候補の owner」という書き方が、ファイル 1 つに owner 1 つが存在することを前提にしていた。**

割れは 2 層で起こる。**初版は上の層しか塞いでいない。**

```
層1  候補のファイル間で owner が割れる        初版が塞いだ
層2  1 つのファイルの中で hunk ごとに割れる    初版が見落とした
```

**両方とも継がない。** 継承の条件を、ファイル単位ではなく hunk 単位で書き直す。

```
継ぐ条件: 候補となるすべての実装ファイルの、すべての hunk の owner を 1 つの集合にし、
          その要素数がちょうど 1 であり、かつ未分類の hunk が 1 つも無い
それ以外: 継がない。unclassified のまま判断へ回す（fail-closed）
```

**「未分類は定まっていない」を明記する（2026-09-07T13:40:00+09:00 追記）。**

**初版のこの条件は「owner がただ 1 つに定まる」とだけ書いた。**
**未分類の hunk をどう扱うかを書いていない。**

```
実装ファイルの hunk 10 個のうち 7 個が agguild、3 個が未分類
```

**ここで「定まっている owner は agguild 1 種類だから継ぐ」と読める。**
**継いではいけない。** 残り 3 個が `official` だった場合、**先に継いだ値は後から覆る。**

**この規則は判定が確定していくたびに再実行する設計である。**
**したがって「ファイルの一部だけが分類済み」は例外ではなく、移行の全期間を通じた通常の状態である。**

**未分類を集合から除いてはならない。** 除くと「まだ分からない」が「分かった」に変わる。
**これは §3.2 が塞いだバグと同じ形である**（未確定の情報を確定した答えとして使う）。

**なお、規則の本体は「層」ではなく 1 つの集合である。**
本節が「2 層ある」と書いたのは誤りを説明するための足場であり、
**規則としては「候補の全ファイルの全 hunk の owner を 1 つの集合にし、要素数 1 かつ未分類を含まない」で足りる。**
**条件が 1 本であるほうが、3 つ目の層を見落とす余地が消える。**

**「そのファイルの owner」という語を使わない。** ファイルに owner は無い。

###### 実測（verifier、2026-09-07）

**第 1 便の 4 ファイルは、4 つとも層 2 の割れを持っていた。**

| 実装ファイル | hunk | 内訳 |
| --- | --- | --- |
| `scripts/watch.sh` | 30 | agguild 24 / official 6 |
| `scripts/lib/actas-lock.sh` | 21 | agguild 19 / **official 2** |
| `scripts/lib/storage.sh` | 15 | agguild 11 / official 4 |
| `scripts/join.sh` | 11 | agguild 9 / official 2 |

`--classify-mechanical` の実装は継承元を `{row['path']: row['owner']}` の辞書で引いており、
**同じ path の行が後の行で上書きされる。** 実質「hunk_id 昇順で最後の行の owner」を継いでいた。

**`tests/test_actas_lock.bats`（6 hunk）が `official` を継いだ。**
`actas-lock.sh` は 21 hunk 中 19 が `agguild` である。**最後の 2 行だけが `official` だった。**

**これは §4.1 が退けた失敗の型（並び順に依存して答えを作る）が、別の場所で再発したものである。**
§4.1 は同数のときの順序を決めない選択をしたが、**ここでは順序が暗黙に答えを決めていた。**

###### `--check` はこれを検出できない

**規則自体が「最後の行」を見ているため、台帳の値と規則の出力は一致する。**
`rule-mismatch` は出ない。**自己整合しているだけで、正しさは示していない。**

これは本書 §3.4 が塞いだはずの型（人が数えた値と機械が出した値の二重管理）とは別の型である。
**値の出どころが 1 つでも、その 1 つが誤っていれば照合は通る。**
**照合は「2 つが同じか」しか言わない。「その 1 つが正しいか」は言わない。**

###### 今回の適用

**第 1 便で継いだ tests/ の 50 hunk は、すべて層 2 の割れを持つファイル由来である。**
**50 行すべてを `unclassified` へ戻し、判断へ回す。**

**割れるということは、その試験が複数の責務にまたがっているということである。**
**それは人が見るべき事実であって、機械が均すべきものではない。**

**「対応が無い」を「実装が公式だから試験も公式」と読み替えないこと。**
**対応が無いのは、名前が違うか、実装がこの差分に無いかのどちらかであって、
どちらも owner を示さない。**

### 3.3 fixture と共有ヘルパ

```
tests/fixtures/**            それを使う試験の owner を継ぐ
tests/test_helper.bash 等    複数の試験が使う。継げないので判断へ回す
```

**`tests/fixtures/**` は、参照している試験が 1 つに定まるときだけ機械的に決まる。**
**2 つ以上の試験から参照されていて owner が割れる場合は、判断へ回す。**

**「どの試験が使っているか」は grep で決まる。** ここは worker が調べられる。

### 3.3.1 判定の補助ツールは、`official` を主張する根拠にならない（2026-09-07T13:10:00+09:00 追記・実測）

**第 2 便以降の分類では、hunk 本文の識別子が上流（`3d06318`）に在るかを数える補助ツールを使う。**
**その適合率を、人手で分類済みの第 1 便 77 hunk に対して測った。**

判定規則: **上流に無い名前を 1 つでも参照していたら `agguild`、1 つも無ければ `official`。**

| 人手 \ ツール | `official` と出す | `agguild` と出す |
| --- | --- | --- |
| `official` | 11 | **2** |
| `agguild` | **18** | 46 |

**食い違い 20 / 77。** 誤りは両方向に出るが、**内訳が非対称である。**

```
ツールが agguild と言い、人手は official      2 件   保守的な向き（判断へ回るだけ）
ツールが official と言い、人手は agguild     18 件   危険な向き
```

**危険な向きが 9 倍多い。**

#### なぜ `official` 側が外れるか

**18 件はいずれも、hunk 本文の名前がすべて上流に在る。**
**しかし hunk が依存している文脈が fork 固有である。**

```
delivery gate のためだけに在る変更   本文は上流の関数しか呼ばない
fork 追加の関数と対で意味を持つ変更  本文の名前は上流にも在る
fork 固有の挙動を説明するコメント     コメントは識別子を含まない
```

**ツールは 1 hunk の中しか見ない。** hunk をまたぐ依存も、fork 固有の設計意図も見えない。

#### 使い方

**このツールは絞り込みにしか使わない。**

```
new > 0    fork 固有の識別子を参照している    -> agguild の候補。本文を読んで確かめる
new = 0    何も言っていない                  -> 必ず本文を読む。official の根拠にしない
```

**`official` は 1 件ずつ人手で確かめる。** `official` と書くことは
「この hunk は単独で上流へ適用できる」と主張することであり、
**それは hunk の外の文脈を見ないと言えない。**

#### 過去の過大評価について

**10 hunk の標本では 9/10 が一致していた。**
**77 hunk では 57/77 である。** 標本が小さすぎた。

**「標本で高い一致率が出た」を、道具の適合率の根拠にしない。**
本ファイル §3.2 の割れの見落としと同じで、**測る範囲を広げたときに初めて見える。**

### 3.3.3 §4 の便の数と実測が合わないのは、実装の欠陥だった（2026-09-07T14:55:00+09:00 追記・実測）

**第 6 便の分類で、`tests/` の内訳が §4 の数と合わないことに気づいた。**
**調べた結果、本書の数のほうが正しく、`implementations_for` の実装に欠陥があった。**

#### 実測（本書の切り方で数え直した）

| 区分 | 実測 | 本書 §2 の表 |
| --- | --- | --- |
| `tests/` の対応あり | 213 / 46 ファイル | 211 / 44 ファイル |
| 対応なし・`test_*` | **83 / 23 ファイル** | **83 / 23 ファイル**（一致） |
| 対応なし・その他 | 27 | 29 |

**2 ファイルが「その他」から「対応あり」へ誤って移っていた。**

#### 原因

```python
stem = normalized_stem(test_path)[len('test_'):]
```

**`test_` で始まるかを確かめずに、先頭 5 文字を無条件で切り落としている。**

| ファイル | stem | 5 文字切った後 | 「対応先」とされた数 |
| --- | --- | --- | --- |
| `tests/fixtures/pm-broker/broker.js` | `broker` | **`r`** | **11** |
| `tests/fixtures/team-work-audit/closed.json` | `closed` | **`d`** | 3 |

**残った 1 文字が実装ファイルの stem と前方一致する。**
`broker.js` の「対応する実装」には **`README.md` が入っていた。**

**既存の `if not stem: return []` は、名前が 5 文字以下のときしか効かない。**
**「`test_` を外した残り」ではなく「無条件に 5 文字外した残り」を見ているためである。**

#### なぜ今まで見えなかったか

**fail-closed に救われていた。** この 2 ファイルの「対応先」は owner が割れているので、
§3.2 の規則が継承を拒む。**誤った対応付けは、誤った結果を出さなかった。**

**対応先の owner が偶然そろえば、fixture が無関係なファイルから owner を継ぐ。**
**そのときは静かに入る。**

**「今は正しく動いている」は「正しい」ではない。**
**この件は、fail-closed が別の欠陥を隠しうることの実例である。**

#### 数が食い違ったことが手がかりになった

**本書 §4 の 83 / 29 は、私が設計時に手で数えた値である。**
**実装が出す値と食い違ったので調べた。**

**§3.4 は「人が数えず、スクリプトが出す」と定めている。**
**その方針は正しいが、今回は人が数えた値が残っていたから欠陥に気づけた。**

## 5. 分類結果の検算

**網羅検査（`--check`）は、分類の正しさを見ていない。**
**全行に `agguild` と書いても通る。**

**したがって別の仕組みが要る。**

### 5.1 標本の再分類

```
1  分類した便が上がったら、その中から 5%（最低 20 行）を抜く
2  抜くのは分類した者ではない。**分類後に抜く**（先に分かると選べてしまう）
3  別の担当が、元の分類を見ずに分類し直す
4  一致率を出す
```

**一致率の閾値を先に決める。**

| 一致率 | 扱い |
| --- | --- |
| 95% 以上 | その便を受け入れる |
| **95% 未満** | **その便を差し戻す。** 全行を分類し直す |

**閾値を後から決めない。** 結果を見てから決めると、通したい方に寄る。

### 5.2 再分類する側にも対照を当てる

**再分類する者が手を抜いていないことを、別に確かめる。**

```
標本へ、**故意に誤った分類を 2 行混ぜる**（元の分類を書き換えて渡す）
再分類でその 2 行が「不一致」として出れば、検算は機能している
出なければ、その検算の結果は使わない
```

**「一致率が高い」ことは、両者が同じように手を抜いていても起こる。**
**今日、私と verifier が同じ誤った値で一致した**（マージ済み設計書 §2.2.4）。
**同じ形である。**

##### 故意の誤りの検出は、一致率とは別に報告する

**標本が小さいと、両者が同じ結果になる。**
440 行の便から 22 行を抜けば、故意の 2 行は 9% にあたる。
**その 2 行を見逃しても、通常の差し戻し（一致率 95% 未満）と同じ結果になる。**

```
報告するもの   1  一致率（%）
               2  **故意の誤り 2 行を検出したか（別項目）**
```

**2 が「検出せず」なら、一致率が何であれその検算は無効である。**
**差し戻しの理由と、検算そのものの失敗を読み分けられるようにする。**

##### 標本の抜き方を決め打ちにする

**「分類後に抜く」だけでは、抜く側が易しい行を選べてしまう。**

```
抜き方   hunk_id の昇順に並べ、n 行ごとに 1 行（n = 便の行数 / 標本数）
         乱数を使うなら、種を記録して再現できるようにする
```

**抜いた結果ではなく、抜き方を先に決める。**

### 5.3 誰が再分類するか

| 便 | 分類 | 再分類 |
| --- | --- | --- |
| 機械的な 294 | worker | **架空の担当を立てない。** 規則の適用は §5.4 の検査で見る |
| 判断が要る 440 | architect | **reviewer**（別の席） |

**機械的な分は、人が再分類しても意味が薄い。** 規則どおりかを機械で見る（§5.4）。

**判断が要る分は、同じ席が二度やっても同じ答えになる。** 別の席が要る。

### 5.4 `--check` と `--gate` の切り分け

**マージ済み設計書 §3.1 は `unclassified` と `no-disposition` を
`--check` の判定として並べている。これは私の書き方の誤りである。**

**そのままだと、台帳を置いた瞬間から分類が終わるまで CI が赤いままになる**（実測。
生成直後の台帳で `--check` が rc=1、`unclassified` 734 件・`no-disposition` 734 件）。

**切り分けの原則を置く。**

```
空である            = まだ分類していない  ->  --gate
空でないが不正な値   = データの誤り        ->  --check
```

| 判定 | どちら |
| --- | --- |
| `missing` / `stale` / `path-mismatch` / `duplicate` | `--check` |
| `malformed` / `header-mismatch` / `unexercised-rule` | `--check` |
| **`owner` / `disposition` / `status` が非空だが規定外の値** | **`--check`** |
| **`owner` / `disposition` / `rationale` が空** | **`--gate`** |
| **`status` が `verified` でない** | **`--gate`** |

#### 5.4.1 実装が出す判定名との対応

**本節は列の意味で書いてある。実装は判定名で報告する。**
**判定名から本書を引けるように、対応を書いておく。**

| 実装が出す判定名 | どちら | 本書での言い方 |
| --- | --- | --- |
| `missing` / `stale` / `path-mismatch` / `duplicate` | `--check` | 網羅 |
| `malformed` / `header-mismatch` / `unexercised-rule` | `--check` | 構造・契約 |
| **`invalid-owner`** | `--check` | `owner` が非空だが規定外 |
| **`invalid-disposition`** | `--check` | `disposition` が非空だが規定外 |
| **`invalid-status`** | `--check` | `status` が非空だが規定外 |
| **`unclassified`** | **`--gate`** | `owner` / `disposition` / `rationale` が空 |
| **`not-verified`** | **`--gate`** | `status` が `verified` でない |
| **`owner-disposition-mismatch`** | `--check` | §1.2 の対応に反する（§5.5 の 1 / 2 / 2b） |
| **`unexpected-pool`** | `--check` | `owner=pool` が 1 件でもある（§5.5 の 3、§1.1） |
| **`rationale-too-short`** | `--check` | `rationale` が非空だが 10 文字未満（§5.5 の 4b） |
| **`rule-mismatch`** | `--check` | 機械的な規則の結果と台帳の値が食い違う（§5.5 の 5 / 6、§3.4） |

**判定名を文書に書いていないと、CI の出力から設計へ辿れない。**

**これで、生成直後の台帳は `--check` が通り、`--gate` だけが落ちる。**
**分類が進むにつれて `--gate` の指摘が減り、全部済んだところで 0 になる。**

**`--gate` は CI で走らせない。** 分類の途中は落ちて当然だからである。

**ただし「誰も実行しないスクリプト」にしない。**
**実行ゲートを開けるときに `--gate` を実行し、その出力を記録することを完了条件とする**（§6）。

### 5.5 機械で見られる整合

**§5.4 の切り分けに従って `--check` か `--gate` へ足す。**
**いずれも分類の中身を知らずに判定できる。**

```
1  owner=official  なのに disposition!=adopt         -> 不整合
2  owner=agguild   なのに disposition!=port          -> 不整合
2b **owner=exception なのに disposition=adopt**       -> **不整合**
   （§1.2 のとおり exception は port か drop のいずれかである。
     移せない事情がある hunk を上流へ提案することはない）
3  owner=pool が 1 件でもある                         -> 想定違い。止める（§1.1）
4  rationale が非空だが 10 文字未満                   -> 実質空欄。書いたことにしている
5  docs/decisions/** 等が agguild 以外               -> §3.1 の規則違反
6  tests/ の対応ありが、対応先と違う owner            -> §3.2 の規則違反
```

**5 と 6 は、機械的な規則を機械で確かめるものである。**
**規則を書いて人が守る形にしない。**

##### `rationale` は空欄と短すぎるものを分ける

**§5.4 の切り分け（空欄は進捗、誤った値はデータ）を `rationale` にも当てる。**

```
rationale が空            まだ書いていない        ->  --gate（実装済み）
rationale が 10 文字未満   書いたことにしている    ->  --check（項目 4）
```

**前者は「まだやっていない」、後者は「やったことにした」である。**
**同じ項目にまとめると、`--check` と `--gate` のどちらへ足すかが決まらない。**

**初版は「空、または 10 文字未満」と 1 項目に書いていた**（verifier の指摘、2026-09-07）。

> **私は `owner` / `disposition` についてこの原則を立てた当人でありながら、
> `rationale` に当てていなかった。**
> **原則を書くことと、原則を自分の書いたものすべてに当てることは別である。**

**10 文字という値に根拠は無い。** 「`port` だから」のような、
**判断を書いていない一言を弾く**ことが目的である。**運用して短すぎ・緩すぎがあれば直す。**
