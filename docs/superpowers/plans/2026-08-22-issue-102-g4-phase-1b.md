# Issue #102 G4 Phase 1B Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking. Execute inline; do not spawn additional agents.

**Goal:** #98 acceptance 後にだけ、G4 audit の complete coverage を append-only SQLite ledger へ保存し、manager の explicit bootstrap と blocked-to-ready transition を安全に実行できるようにする。

**Architecture:** Phase 1B は reviewer が独立に reject できる三つの PR に分ける。第一 PR は internal ledger schema と history trigger のみ、第二 PR は exact manager による all-or-nothing bootstrap、第三 PR は expected revision と fresh predicate observation を要求する blocked-to-ready transition である。既存 G4 audit の GitHub read-only boundary は維持し、すべての mutation は local SQLite transaction に閉じる。

**Tech Stack:** Bash 3.2+, Node.js standard library, sqlite3, existing G4 contract/audit modules, Bats with PATH-injected fake gh fixtures.

**Spec:** docs/decisions/2026-08-21T210215_issue-102-g4-implementation-design.md

**Decision record:** https://github.com/kappaseijin/agmsg/issues/102#issuecomment-5369510068

## Global Constraints

- A2 is fixed: the common agmsg G4 validator and append-only local ledger are the authority. Project repositories contribute only versioned G4 packs.
- B1 is not in this phase. g4-pull remains a Phase 2, exact-owner-only PR; do not add it, change legacy claim authority, create a claim, send dispatch, or write GitHub.
- C1 is fixed: only an exact manager seat may record a transition, and blocked-to-ready requires the current ledger row's release predicate to be freshly observed true in the same operation.
- Phase 1B implementation may begin only after the producer records fresh evidence that #97 is merged and #98 acceptance is complete. Issue state alone is never acceptance; a missing acceptance artifact, a failed roster JSON check, or an ambiguous artifact is a hard stop.
- The #98 user decision is fixed: each target team's PM executes roster-normalize --apply in that target's own Issue/PR. agmsg does not perform target-team --apply.
- g4-audit remains read-only. It may not initialize SQLite, mutate the new G4 tables, invoke a GitHub write method, or update labels.
- Every Phase 1B mutating command must use BEGIN IMMEDIATE, preserve all prior revision rows, and roll back completely when any guard fails.
- G4 current state is separate from team_work_current and team_work_dispatch_current. Do not modify #97 dispatch recovery behavior in any Phase 1B PR.
- All G4 output is canonical JSON. Pack, entry, coverage, audit, and snapshot digests use the existing canonical SHA-256 representation.
- README is the user-facing source of truth. Each newly public command must be documented in the same PR that exposes it.

### Shared G4 ledger record

The PR 1 schema uses source identity as the stable key. The implementation must create these two tables in scripts/internal/init-db.sh, after the existing team-work schema and before the script returns:

~~~sql
CREATE TABLE IF NOT EXISTS team_work_g4_current (
  team TEXT NOT NULL,
  source_repository TEXT NOT NULL,
  source_number INTEGER NOT NULL CHECK (source_number > 0),
  state TEXT NOT NULL CHECK (state IN ('ready', 'blocked', 'unknown')),
  owner_seat TEXT NOT NULL,
  work_kinds_json TEXT NOT NULL CHECK (json_valid(work_kinds_json)),
  revision INTEGER NOT NULL CHECK (revision > 0),
  pack_digest TEXT NOT NULL,
  entry_digest TEXT NOT NULL,
  coverage_digest TEXT NOT NULL,
  audit_digest TEXT NOT NULL,
  basis_json TEXT NOT NULL CHECK (json_valid(basis_json)),
  blocker_json TEXT,
  evidence TEXT NOT NULL,
  last_action TEXT NOT NULL,
  last_actor TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (team, source_repository, source_number),
  CHECK ((state = 'blocked' AND blocker_json IS NOT NULL) OR
         (state IN ('ready', 'unknown') AND blocker_json IS NULL))
);

CREATE TABLE IF NOT EXISTS team_work_g4_revisions (
  team TEXT NOT NULL,
  source_repository TEXT NOT NULL,
  source_number INTEGER NOT NULL CHECK (source_number > 0),
  revision INTEGER NOT NULL CHECK (revision > 0),
  previous_revision INTEGER,
  action TEXT NOT NULL,
  actor TEXT NOT NULL,
  snapshot_json TEXT NOT NULL CHECK (json_valid(snapshot_json)),
  created_at INTEGER NOT NULL,
  PRIMARY KEY (team, source_repository, source_number, revision)
);
~~~

Insert and update triggers on team_work_g4_current must append exactly one canonical snapshot to team_work_g4_revisions. BEFORE UPDATE and BEFORE DELETE triggers on team_work_g4_revisions must raise ABORT with the stable message team_work_g4_revisions is append-only.

**Interfaces:**

- Public command:

  ~~~text
  team-work.sh g4-transition <team> <g4-state-pack.json> \
    <repository> <issue-number> <expected-revision> <manager-seat> <evidence>
  ~~~

- g4-transition accepts exactly eight arguments after the script name. repository, issue-number, and expected-revision select one current G4 row; manager-seat and evidence are mandatory.
- transitionG4 first validates the new pack, reads the exact current row, and confirms current.revision = expected-revision, target entry.revision = expected-revision + 1, source/ownerSeat/workKinds/basis remain equal, and the target changes from blocked to ready.
- The operation runs a fresh scope audit for the submitted pack and directly evaluates the releasePredicate saved in the current blocked row. It admits the transition only when coverage is complete and that predicate observation is true.
- The command updates exactly one current row and relies on the PR 1 update trigger to append exactly one revision. It has no path for a generic state transition, claim, g4-pull, dispatch, or GitHub write.

- [ ] **Step 1: Add failing transition tests**

  In tests/test_g4_transition.bats, bootstrap a blocked entry through the public bootstrap command, then submit a revision-2 ready entry. Add tests for:

  1. a true issue_closed predicate creates exactly one blocked-to-ready revision with previousRevision 1 and persists fresh audit/coverage/evidence digests;
  2. false and GitHub-unavailable predicates reject with no current or revision checksum change;
  3. stale and skipped expected revisions reject with no mutation;
  4. wrong manager, human seat, owner seat, missing evidence, wrong repository, and wrong issue number reject with no mutation;
  5. changed ownerSeat, workKinds, basis, or source rejects with no mutation;
  6. ready-to-blocked, unknown-to-ready, and blocked-to-unknown inputs reject as unsupported in Phase 1B;
  7. fake-gh records only read operations and no GitHub write or dispatch is invoked.

- [ ] **Step 2: Export the needed fresh-observation primitive**

  Keep g4-audit's CLI behavior unchanged. Ensure its module export includes evaluatePredicate and runAudit so g4-ledger.js can run the same read-only predicate evaluator used by audit instead of reimplementing GraphQL behavior. In tests/test_g4_audit.bats, remove g4-transition from the future-command-unavailable loop; retain g4-pull as the only unavailable future command.

- [ ] **Step 3: Implement strict transition guards**

  Load current state with readG4Current. Reject absent rows, non-blocked rows, any input revision other than current + 1, and any immutable source/owner/workKinds/basis change before starting SQL. Run the fresh audit and evaluate the saved current blocker releasePredicate. Treat false, unknown, coverage mismatch, and source failure identically as no-mutation rejections.

- [ ] **Step 4: Perform one guarded update**

  Use runG4Transaction with an UPDATE guarded by team, source identity, state = blocked, revision = expected-revision, ownerSeat, old entry digest, and the immutable fields. Set state ready, blocker_json NULL, revision expected-revision + 1, new pack/entry/coverage/audit digests, evidence, last_action g4-transition, last_actor managerSeat, and updated_at. The result SQL must return the changed current row; changes other than exactly one are a rollback.

- [ ] **Step 5: Document the transition contract**

  Add the copyable command to README.md. State the expected-revision requirement, exact-manager authority, only supported blocked-to-ready edge, fresh true predicate requirement, immutable owner/workKinds/basis fields, local append-only ledger result, rejection/retry semantics, and no GitHub/dispatch side effects.
